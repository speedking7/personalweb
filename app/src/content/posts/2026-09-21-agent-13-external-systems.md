上一篇的结论是：写份需求说明，再去找人。

**但那份说明是写给工程搭档的**。这一篇要写的是另一份，给的是**系统那边的人**——他手上有你要的数据，可他不归你管，也不欠你。

这一篇讲你去了之后会发生什么。

而你多半会听到三种回答：**「这个系统没有接口」「接口有，但你没权限」「接口在，不过那个人已经走了」。**

三种听起来都像拒绝，**而要找的人完全不同**。分不清楚，那份写得很好的需求说明就会被拿去敲一扇打不开的门。

## 学习目标

| | 你能做到 |
|---|---|
| 一 | 盘点出你要的那个系统现在能调什么 |
| 二 | 分清「拿不到」是哪一种，并说出各该找谁 |
| 三 | 写出一份对方能直接排期的接口申请 |
| 四 | 说清不约定 SLA 与故障责任人，上线之后谁背锅 |
| 五 | 在接口做不出来时选一条退路，并说出它在哪儿收费 |

产出物是一份接口盘点表、一份接口申请、一份退路方案。

**前面教的都是「怎么想清楚」，这一篇教的是想清楚之后怎么要到**。这部分工作量经常超过搭 Agent 本身——而它恰好是业务顾问的强项。

## 一、先别提需求，先盘点现在有什么

多数人一上来就说「我要一个查单据的接口」。这句话会被打回，因为对方不知道这是要干什么，也不知道要花他多少工夫。

**先盘点**。问的是「现在已经有什么」，不是「能不能给我做一个」。

通道一共四类：

| 通道 | 大概是什么 | 要问出来的 |
|---|---|---|
| API | 系统开放的调用地址，最正规的一条 | 谁负责——**要一个名字，别接受「系统团队」** |
| MCP | 给 AI 用的标准化接入方式 | 是谁搭的，有谁用成过 |
| RPA | 让机器人模拟人去点界面 | 内部流程团队还是外包，合同到期没有 |
| 定期导出文件 | 每天/每周导一份表出来 | 是系统自动导的，还是某个人手工导的 |

**最后一列是这张表的全部重点**。前两列你查文档能查到，最后一列只能问人。

而一条跑得好好的通道，如果维护者是「三年前某个人写的脚本」，它跟没有接口的区别**只是暂时还没坏**。

### MCP 不是现成的

盘点的时候，MCP 最容易被高估——它名字里带着「标准化」，听起来像插上就能用。

[上一篇提过那次实测](https://blog.yingtongxue.cn/#/blog/2026-09-19-agent-12-nocode-boundary)：另一个项目里把外部服务按两种标准配置接进来，两种都解析成功、绑定成功，**而 Bot 的工具集里一次调用都没有**。

盘点表里 MCP 那一行，**要问的不是「有没有」，是「有谁在用它，用成过吗」**。没有人用成过的通道，登记的时候当「没有」算。

## 二、「拿不到」有四种，各找各的人

盘点完你会撞上「拿不到」。

开头那三种是**你会听到的说法**。而底下的成因有四种——**多出来的那一种你听不出来**，因为对方会把它说成前两种里的任意一句：既可能说「没有这个接口」，也可能说「这个你没权限看」。

四种找的人完全不同。

| 你听到的 | 真正的问题 | 找谁 | 你要准备什么 |
|---|---|---|---|
| 压根没有接口 | 要排一次开发 | 系统 Owner | 一份接口申请，见第三节 |
| 接口有，你没权限 | 授权范围 | 数据 Owner | 权限申请，写清四维 |
| 上面两句里的任意一句 | **源系统里就没有这个字段** | 源系统的**业务** Owner——判字段存不存在的是他，不是 IT | 见下面那条判据 |
| 接口在跑，但没人维护 | 责任真空 | 对方部门的负责人，要他**指派一个具名的人** | 指不出来就按「没有接口」办，见第五节 |

前两种是常规流程，**后两种是这一节的重点**。

### 第三种：源系统里没有的东西，接口给不出来

[第 07 篇立过一条判据](https://blog.yingtongxue.cn/#/blog/2026-09-14-agent-07-action-layers)：**拆的粒度不由你想象，由系统实际有哪些状态决定**。那一篇讲的是动作——演示制度里没有草稿态，所以「它建、人审、再提」这条路设计不出来。

同一条判据往前挪一步，就是字段：**你要的那个字段，源系统里存不存在。**

不存在的话，接口做出来也是空的。这时候要做的不是催开发，是回去改需求——要么换一个已有的字段凑合，要么走一次源系统的变更（那是另一件事，时间以季度计）。

**怎么先查**：别问技术，问业务。**找一个天天用那个系统的人，让他把那个页面打开给你看一眼**。页面上没有的东西，接口里多半也没有。

### 第四种最坏，因为它看起来是通的

「接口在跑，但没人维护」——这一种最容易被当成「有」。

测的时候它通，上线的时候它通，然后某天它不通了，而**找不到任何一个有义务修它的人**。

[这跟上一篇讲的那件事是同一个形状](https://blog.yingtongxue.cn/#/blog/2026-09-19-agent-12-nocode-boundary)：绿灯不等于通车。只不过上一篇的绿灯是平台状态，这一篇的绿灯是「它现在能调通」。

**判据是一句话：说得出名字吗。**

问「这个接口谁负责」，得到的答案如果是一个部门、一个系统名、或者「以前是老王，他现在不管了」，那这条通道在你的盘点表里就该记成**红色**——它能用，但没有人对它的可用性负责。

这一行不解决，不是不能上线，而是**上线之后它一定会变成你的问题**。第四节讲怎么解决。

## 三、申请书：写成对方能排期的样子

一份估不出工作量的申请，对方能做的只有打回，或者无限期搁置。

「给我查单据的权限」估不出。下面这份估得出：

| 项 | 写什么 | 演示项目里的样子 |
|---|---|---|
| 要干什么 | 一句业务话，不是技术话 | 提单助手要能告诉提单人「你那张单现在走到哪一步了」 |
| 场景 | 什么情况下会调到你 | 用户在对话里问某张单的进度时 |
| 对象 | 能碰哪些数据 | 只限当前用户本人提交的单 |
| 字段 | 具体哪几个 | 单号、当前状态、各节点时间、当前处理人 |
| 操作 | 读还是写 | **只读。不允许任何写操作** |
| **以谁的身份调** | 要几个账号、怎么分 | 只读查询一个账号；将来要写，**另开一个，不在这个账号上加权限** |
| 频率 | 大概多少量 | 每天几十次，峰值不超过每分钟 10 次 |
| 怎么算做成了 | 验收怎么验，**由你定不由他定** | 拿三张真单号调一次，返回的状态与单据系统界面上一致 |
| 什么时候要 | 给对方排期用 | 希望某月某日前可用，不是「越快越好」 |

第三到第五行——**对象、字段、操作**——直接抄[第 08 篇那张权限矩阵](https://blog.yingtongxue.cn/#/blog/2026-09-15-agent-08-tool-whitelist)，你已经填过一遍了。

**但「场景」那一行要重写**。第 08 篇问的是「它在哪儿能用」，管的是你自己的 Agent；这里问的是「什么情况下会调到对方」，管的是对方的容量评估。抄错了，对方看了还是不知道你要干什么。

**「以谁的身份调」这一行最容易漏，而它才是「只读」真正落地的地方**。[第 08 篇那条警告在这儿生效](https://blog.yingtongxue.cn/#/blog/2026-09-15-agent-08-tool-whitelist)：只读查询和新建单据要挂在两个账号上，而不是一个账号加权限——**加完那一下，原来那个只读的工具也跟着能写了**。只写「操作：只读」，对方给你的多半就是一个账号加只读权限。

「怎么算做成了」那一行是[从上一篇平移过来的](https://blog.yingtongxue.cn/#/blog/2026-09-19-agent-12-nocode-boundary)，也是这两份申请唯一能共用的一行。没有它，交付标准就是「接口通了」——而做回来是错的，你都说不清哪儿错。

### 一个现成的例子

[第 10 篇结尾留下过一个具体诉求](https://blog.yingtongxue.cn/#/blog/2026-09-17-agent-10-logs-and-versions)：给提单要素加一格关联标识，用来把 Agent 那边的会话跟单据串起来。

按上面这张表写出来是这样：

> **要干什么**：出了事能从一张单回查到当时 Agent 说了什么。
> **场景**：Agent 代提的单，提交时带上。
> **对象**：只有 Agent 提交的那些单。
> **字段**：新增一格「关联标识」，纯文本。
> **操作**：写入一次，此后只读。
> **关键约束**：**这一格不参与任何流程判断**——不影响受理、不影响审批、不进检索条件。

最后那一行是整份申请里最值钱的。**它把对方的评估范围从「改一个流程系统」缩成了「加一个不影响流程的备注格**」——这两件事在对方眼里根本不是同一件事。

## 四、SLA 与故障责任人：不谈这一项，锅就是你的

接口挂了，Agent 答不出来或者答错了，用户找的是你——因为在他眼里那个 Agent 是你的。

**那你往下找谁**？这个问题要在上线之前有答案，而且要有名字。

要谈的就三件事，每一件都落在提单助手身上：

| 要约定的 | 具体是什么 | 落到提单助手就是 | 不约定会怎样 |
|---|---|---|---|
| 多久算超时 | 调用多久没返回算失败 | 超时之后它该说「查不到，请直接看单据系统」，而不是接着编 | 它一直等，用户看着转圈；或者更糟，它自己补一个状态出来 |
| 坏了多久修 | 报障之后的响应与恢复时限 | 这个数决定你的运行 Owner 要不要准备一条人工兜底 | 「我们看一下」，然后没有然后 |
| 谁通知谁 | 对方改字段、改定义、计划停机，怎么提前告诉你 | 对方把「变更类型」的选项改了一个，你那条只读接口读回来的东西就变了意思 | 周末升级，周一它全线答错，而你以为是模型的问题 |

第一行接的是第 15 篇那五种必须停下来的情况里的一种：**工具失败的时候，它该停，不该猜。**

第三行最容易漏，**而它是三件里最便宜的**——多数情况下只需要把你加进对方的变更通知名单。而它的代价最隐蔽：**字段定义变了，接口照样通，返回的数也照样有，只是意思不一样了。**

**这三件的答案要写进[第 05 篇那格「工具和接口权限」](https://blog.yingtongxue.cn/#/blog/2026-09-10-agent-05-intake-form)**，连同对接人的名字。没有名字的那一行，等于这一项没谈。

### 对面是外部厂商的时候，这三件不是一回事

上面那套按内部系统团队写的。对方是外部厂商，三件事的性质全变：内部靠排期和人情，外部靠合同条款——**没写进合同的 SLA，等于没有。**

而外部还多一件内部没有的：**合同到期怎么办**。厂商不续约、产品下线、被收购，你的接口会在一个跟你无关的日期停掉。这一条要跟采购确认，不是跟对接人确认。

### 三件一件都谈不成的时候

这就是第二节那第四种——**责任真空**。到这一步只有两条路：

**往上要**。让你自己的 IT Owner 去对方部门要一个具名责任人。这件事你个人要不来，因为它本质上是两个部门之间谁担责的问题——而[第 05 篇登记表里那格空着的 Owner](https://blog.yingtongxue.cn/#/blog/2026-09-10-agent-05-intake-form)，后果就在这儿现形。

**往下退**。要不到，就把这条通道记成「没有接口」，走下一节。

**别选第三条路**——「先上着，回头再说」。那条路上，接口哪天坏的你不知道，坏了之后 Agent 答的是什么你也不知道。

## 五、接口做不出来：三条退路，各自在哪儿收费

有时候答案就是「做不了」——没排期、没预算、或者那个系统明年就要下线。

三条退路，**没有一条是免费的**，区别只在它在哪儿收费。

| 退路 | 怎么做 | 在哪儿收费 | 顺带作废了什么 |
|---|---|---|---|
| 定期导出文件 | 让对方每天导一份表，传进知识库 | **时效**：Agent 看到的永远是昨天的数据 | 导来的是整张表，[第 08 篇那条「只限本人提交的单」当场失效](https://blog.yingtongxue.cn/#/blog/2026-09-15-agent-08-tool-whitelist)；而且这份文件进了知识库，从此要按[第 11 篇管来源、版本、有效期](https://blog.yingtongxue.cn/#/blog/2026-09-18-agent-11-knowledge-base) |
| RPA 抓屏 | 让机器人模拟人去点那个界面 | **脆**：这类退路最常见的死法是对方改了一次界面，而且坏得无声无息 | 它得用某个人的账号去点——[第 08 篇那条「只读和可写分两个账号」跟着破](https://blog.yingtongxue.cn/#/blog/2026-09-15-agent-08-tool-whitelist)，那个账号能做什么它就能做什么 |
| 人工录入 | 人定期把关键信息填进来 | **人**：这笔工时会落到某个人头上，而这类安排最常见的结局是停掉 | [第 10 篇那条关联标识挂不上](https://blog.yingtongxue.cn/#/blog/2026-09-17-agent-10-logs-and-versions)，追溯链断在录入那一步 |

**最后一列才是这张表的重点**。前三列讲的是技术代价，最后一列讲的是：这条退路会把你前面几篇刚建起来的控制项拆掉一个。

选哪条，判据不是「哪个技术好」，是**这个场景能不能同时接受那两样代价**。

- 提单助手要查的那几份制度原文在文档系统里，接口要不到——**每月导一次就够，制度本来也不天天变**。
- 提单助手查「我那张单现在到哪了」，昨天的数据等于没用——**这条退路不成立**，要么等接口，要么这个功能先不做。

**最后那半句要敢说出口**。这个功能砍掉，比带着一个每次都答错的功能上线强——而后者会把前面十二篇的控制项一次性作废，那些东西攒的就是「它说的话能信」这一件事。

### 退路也要写进登记表

退路不是临时方案，它**就是方案**。写进登记表的时候要同时写清两件事：**它的代价是什么**，以及**什么条件下切回正式接口**。

不写第二件，退路会变成永久状态——这是这一行最常见的结局。

## 六、产出物

三样东西。

**其一，接口盘点表**，你要的那个系统一行一条通道：

| 通道 | 有没有 | 有谁用成过 | 负责人叫什么名字 |
|---|---|---|---|
| API | | | |
| MCP | | | |
| RPA | | | |
| 定期导出 | | | |

**中间那一列专治 MCP 那一行**：配上了不算，有人用成过才算。第三列答不出名字的，这条通道记成红色。

**四行的第三列全是空的，你面对的就不是技术问题。**

**其二，一份接口申请**，照第三节那九行写。

**其三，退路方案**，照第五节那张表选一条，写清代价与切回条件。

填完自查五条：

| | 自查 |
|---|---|
| 一 | 盘点表里 MCP 那一行，你是按「配上了」还是按「有人用成过」填的 |
| 二 | 「以谁的身份调」那一行写了没有。只写「只读」，拿回来的多半是一个账号加只读权限 |
| 三 | 你要的每个字段，在那个系统的界面上真的看得见吗 |
| 四 | 故障责任人那一格填的是名字，还是部门 |
| 五 | 退路方案里有没有「什么条件下切回来」 |

## 七、下一篇讲什么

第四部分到这里只剩最后一篇，而它要回答一个从第 07 篇就挂着、这一篇又添了一笔的问题。

现在手上有一堆「不许做」：不许替提单人定级、不许在窗口外发起上线、不许往刚申请到的那个只读接口里写东西。

**这些不许做的，由谁来执行？**

[上一篇给了半个答案](https://blog.yingtongxue.cn/#/blog/2026-09-19-agent-12-nocode-boundary)：前三层那些换动作就绕开了，真要在动作发生那一刻拦住的才轮到门禁。第 14 篇讲另外半个——**那道门该放在哪一层**。

放在提示词里等于没放，这件事你已经知道了。但放进工具层就够了吗？

**第 14 篇会摆一次实测：门禁配在工具层，而 Bot 用平台原生的工具读到了同一个地方。**
