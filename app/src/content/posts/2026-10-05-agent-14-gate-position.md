前面十三篇，你手上攒下了一堆「不许做」。

不许替提单人给风险等级、不许在窗口外发起上线、不许用那个只读账号写东西、不许拿索引里那句摘要当业务依据、不许读取已经废止的那份知识。

这一篇问一个问题：**这些「不许做」，现在由谁在执行？**

[第 12 篇给过半句答案](https://blog.yingtongxue.cn/#/blog/2026-09-19-agent-12-nocode-boundary)：答案是「提示词」的，就是没执行。

这一篇给另外半句——**那该放在哪儿。**

## 学习目标

| | 你能做到 |
|---|---|
| 一 | 分清哪些「不许做」根本没有位置能拦 |
| 二 | 说出判断门禁位置的那一条判据，以及读类与写类为什么不一样 |
| 三 | 说清那次实测发生了什么，以及你从哪儿看得出它在你身上发生了 |
| 四 | 判断一道门能不能由 Agent 自己执行 |
| 五 | 说出「哪些交给 AI、哪些必须确定」这条线按什么画 |

产出物是一张执行位置表：每一条「不许做」，填由谁执行。

## 一、先划掉没有位置能拦的那几条

**不是所有「不许做」都有地方放一道门**。这是这一篇最容易跑偏的地方，而开头那五条里有两条根本没有位置能拦。

分法不是按层号，是按一件事：**它要不要伸手去够什么东西。**

| 这件事 | 有没有位置能拦 | 执行形态 |
|---|---|---|
| **说出口的那一刻就已经生效** | 没有 | 换动作、换下游 |
| **要伸手去够某个东西才做得成** | 有——就在它伸手的那个地方 | 门禁 |

「不得替提单人给出风险等级结论」属于前一类。[第 07 篇点过这件事](https://blog.yingtongxue.cn/#/blog/2026-09-14-agent-07-action-layers)：**给建议不需要工具**，它一个工具都没有的时候就三次主动要判风险等级。没有工具，就没有拦截点——你不可能在一句话出口之前拦住它。出路是换动作：把「它判」改成「它把判据摆出来，人判」。

而「读某个文件」「往单据系统写一个字段」属于后一类。它们**都要伸手去够 Agent 之外的东西**——前者够文件系统，后者够对方的接口。伸手的那一下，就是拦截点。

**注意这条分法跟层号不重合**。第 07 篇说过「不给那个工具」这条手段管第四层到第七层，那说的是**那一条手段**的射程，不是门禁的。读取是第一层，而第 07 篇自己就举过一条第一层的禁止动作：**不得读取本空间知识库之外的文件（一）**。

所以开工前先把清单过一遍，划掉「说出口即生效」那几条。剩下的才是这一篇的对象。

## 二、判据只有一条：它够不着吗

剩下那些，门禁该放哪儿？

判据只有一句：**门禁要放在 Agent 够不着的地方。**

而这里的「够不着」要问得更准一点——**这道门由谁来判定。**

| 门配在哪 | 谁判定 | 结果 |
|---|---|---|
| 系统提示词里 | 它自己——**它就是读提示词的那一个** | 拦不住 |
| 配在它调用的某个工具里 | 那个工具自己判，但同一台机器上还有不经过它的路 | **实测被绕过** |
| 对方系统那一侧 | 对方系统收到请求之后自己判 | 拦得住 |

第一行你已经知道了：[提示词能规定「做什么」，规定不了「不做什么」](https://blog.yingtongxue.cn/#/blog/2026-09-18-agent-11-knowledge-base)。

第二行要摆开讲。

### 那次实测：门禁没被攻破，是那条路自己坏了

另一个项目里给 Bot 配过一道工具层的门禁：某些文件不许读，规则配在工具这一层。

然后它读到了那些文件。

**但过程不是你想的那样**。它没有去试探、没有找漏洞。真实的经过是：**给它的那段中文指令经过命令行管道时被损坏了**——那条带门禁的路自己不通了。而它接下来做的事非常自然：换了一个平台原生的工具，读到了同一个地方。

那个原生工具上没有门禁。

**这比「它想绕」值得警惕**。「它想绕」至少是可预期的：你能想象一个对手，你能去堵。而这一次是——那条路一坏，它换了一条，而另一条上什么都没配。

这只是一次观察，别把它读成「它一定会这么干」。**能从这里拿走的是一条设计约束：你的门禁不能建立在「那条带门禁的路一直通」这个前提上**。

根因很清楚：**Agent 手上有 shell**。给它划的范围写在配置里，而它有一个不看那份配置的办法。

### 你从哪儿看得出它在你身上发生了

这件事最难的地方是它没有任何报错。所以要知道去哪看。

[第 08 篇已经把这处记录指出来了](https://blog.yingtongxue.cn/#/blog/2026-09-15-agent-08-tool-whitelist)：算数的只有平台记下来的那一次工具执行——回答正文上方那一小组带对勾的行。

**看 `Read` 那几行上的文件名**，它们在不在你划掉的范围里。别按工具名判——你平时每一次正常的回答，轨迹里本来就全是平台原生的工具。

文件名落在划掉的范围里，这件事就正在发生；而那一行可以点开，点开就是那份文件。

这也是[第 08 篇那张天花板表的确切含义](https://blog.yingtongxue.cn/#/blog/2026-09-15-agent-08-tool-whitelist)：白名单减少的是它顺手做错事的机会，**它从来不是最后一道门**。门失效的时候你看得见，靠的是平台那条轨迹，不是白名单。

### 写类有真门，读类在这个平台上没有

写类动作：**你往对方系统写不进去，因为那个账号在对方那边就没有写权限**。这道门 Agent 绕不过，因为它根本不在 Agent 那一侧。

[所以上一篇那件事才是真门禁](https://blog.yingtongxue.cn/#/blog/2026-09-21-agent-13-external-systems)：只读查询和新建单据挂在两个账号上，而不是一个账号加权限。**「操作：只读」写在提示词里、写在工具描述里、写在需求说明里，都不算门禁**——只有当那个账号在对方系统那边确实没有写权限时，这道门才成立。

读类动作不一样。它要够的是自己空间里的文件，而那些文件就在它手边。

**把文件挪个目录，也不算够不着**。[第 11 篇说过](https://blog.yingtongxue.cn/#/blog/2026-09-18-agent-11-knowledge-base)，它那条 `find` 是从空间根往下递归列文件的——你没有任何依据认为换个目录它就够不着了。而且第 11 篇那套废止做法本身就不是删除：搬进 `_closed/`、文件留着，从「能被引用」变成「只能被追溯」。挪位置从来挡不住它读到。

所以[第 11 篇留下的那三条](https://blog.yingtongxue.cn/#/blog/2026-09-18-agent-11-knowledge-base)——`AGENTS.md` 里的检索预算、索引文件头上那句「别拿索引当业务依据」、废止之后的「对外回答只用已发布区」——在这个平台上**没有一道你点得出来的门**。出路还是第 11 篇给过的那一条：**改那份文件本身**，把旧结论删干净，只留一行「本条已于某日废止，现行口径见某某」。挡不住它读，就让它读到正确的东西。然后看轨迹。

## 三、谁执行：它自己跑门禁，等于没跑

位置定完还有一问，而这一问比位置更容易被忽略：**这道门由谁来执行。**

最常见的错法是让 Agent 自己跑一遍检查，然后报告结果。

**它自己跑完门禁告诉你「过了」，跟它直接说「我做完了」是同一句话。**

[第 04 篇立过这条](https://blog.yingtongxue.cn/#/blog/2026-09-09-agent-04-approve-the-list)：**报告的人，不能是被检查的那个人**。[第 09 篇把它说得更细](https://blog.yingtongxue.cn/#/blog/2026-09-16-agent-09-approval-points)：**不能由被检查的那一方执行，也不能由刚批过的那个人执行。**

这一篇把两句合起来，给一条可查的判据：

> **这道门的执行者，和被这道门检查的对象，是不是同一个。**

是，这道门就不存在——不管它的逻辑写得多严密。

### 人这一侧也有同一个毛病

上面那条判据不只管 Agent。[第 09 篇那句话的后半截讲的是人](https://blog.yingtongxue.cn/#/blog/2026-09-16-agent-09-approval-points)：**也不能由刚批过的那个人执行。**

理由是同一个。他十分钟前刚批过这份清单，此刻让他去核「执行的和批的是不是同一份」——**他核的是自己十分钟前的判断**，而人对自己刚做过的判断天然宽容。

做法两条，按你手上有多少人选：

| 手上有几个人 | 做法 |
|---|---|
| 两个以上 | 批的人和核的人分开，这是最省事的 |
| 就一个人 | 这道校验不能靠人，得让机器比对——[第 09 篇那个由内容算出来的标识就是干这个的](https://blog.yingtongxue.cn/#/blog/2026-09-16-agent-09-approval-points) |

**第二行是多数小项目的真实处境**。人手不够的时候，出路不是「让他再仔细看一遍」，是**把这道校验从人身上挪到机器身上**。

### 两个容易漏的形态

| 形态 | 为什么也算「自己检查自己」 |
|---|---|
| Agent 调一个「校验工具」，工具返回通过 | 调不调这个工具是它决定的。它可以不调，然后说调过了 |
| 校验逻辑写在 Agent 的提示词里，让它执行前自查 | 同上，而且更隐蔽——界面上完全看不出它自查了没有 |

第一行要跟[第 09 篇那条标识校验](https://blog.yingtongxue.cn/#/blog/2026-09-16-agent-09-approval-points)对上：那道校验之所以立得住，是因为**标识由冻结那一刻的内容算出来**，而且**执行前后各比对一次**——比对这个动作不由它发起，结果也不经它的口。

## 四、结果怎么传回来

门禁在外面跑完了，结果要回到你手上。这最后一步同样有讲究。

**不能由 Agent 转述，也不能由跑它的那个人口头说。**

[第 10 篇那三类来源在这儿正好用上](https://blog.yingtongxue.cn/#/blog/2026-09-17-agent-10-logs-and-versions)：门禁跑了没有、结果是什么，这是「记录」；Agent 说「校验通过了」，这是「生成」；人说「我核过了」，这是「声明」——而声明是三类里最软的那一类，旁边必须挂上他当时批的那份东西。

[第 04 篇给过那条真实流水线的做法](https://blog.yingtongxue.cn/#/blog/2026-09-09-agent-04-approve-the-list)：**能进清单的不是「它说测试过了」，是「谁跑的、什么时候跑的、结果在哪」。**

三样都要，缺一样你就核不动：

| 要回来的 | 缺了会怎样 |
|---|---|
| 谁跑的 | 你不知道跑它的是不是被检查的那一方 |
| 什么时候跑的 | 你不知道它跑的是改之前还是改之后的那一版 |
| 结果在哪 | 你只有一句结论，没有可回去看的东西 |

**最后一行是判据**：门禁的结果要有一个 Agent 改不了的落脚处——对方系统里的一条拒绝记录、单据系统里的一条状态、任务系统里的一条审批记录。**落在 Agent 的会话里，它就不是记录了。**

## 五、产出物：一张执行位置表

把你那张「不许做」清单逐条过一遍：

| 不许做什么 | 要伸手够什么 | 由谁执行 | 结果落在哪 |
|---|---|---|---|
| 不得替提单人给出风险等级结论 | 什么都不用够 | **没有位置能拦**——换动作 | —— |
| 不得拿索引里那句摘要当业务依据 | 什么都不用够 | **没有位置能拦**——改索引文件本身 | —— |
| 不得读取已废止的那份知识 | 空间里的文件 | **没有你点得出来的门**——改文件本身，看轨迹 | 轨迹里的文件名 |
| 不得用只读账号写任何东西 | 对方的接口 | 对方系统那一侧：那个账号本来就没有写权限 | 对方会不会留下拒绝记录——要问出来 |
| 不得在窗口外发起上线 | 上线系统 | 上线系统按窗口拒绝，**且「变更类型」不能由它填** | 要问出来 |

最后一行要单独看。演示制度里紧急修复不受窗口限制，所以[第 08 篇专门把「变更类型」从它的可写字段里拿掉](https://blog.yingtongxue.cn/#/blog/2026-09-15-agent-08-tool-whitelist)，由提单人自己选——它要是填得到那一格，窗口这道门它就够得着了。**一道门成不成立，要连它的旁路一起看。**

五条里有三条，在这个平台上没有你点得出来的门。**这是正常的**，而且比给每一条都配一道假门要好。

填完自查四条：

| | 自查 |
|---|---|
| 一 | 第三列里有没有哪一行填的是「提示词」。有，那一条就是没执行 |
| 二 | 第三列里有没有哪一行填的是 Agent 自己。有，那道门不存在 |
| 三 | 「没有位置能拦」那几行，换动作的方案写了没有。没写，那一条也没执行 |
| 四 | 第四列里有没有哪一行落在 Agent 的会话里 |

**填回登记表**：「由谁执行」这一列归[第 05 篇那格「人工审批点」](https://blog.yingtongxue.cn/#/blog/2026-09-10-agent-05-intake-form)——第 09 篇填的是「这道门放哪儿、谁来批」，这一篇补的是「这道门由谁跑」。「结果落在哪」那一列归「运行监控和复盘机制」，而[那一格第 11 篇已经点过挤了四样](https://blog.yingtongxue.cn/#/blog/2026-09-18-agent-11-knowledge-base)——你自己那份登记表加得动，就另开一格。

## 六、这条线按什么画

第四部分到这里完了。回头看这四篇讲的是同一件事的四个侧面：知识库是它看得见什么，无代码边界是你做得了什么，外部接入是你要得到什么，门禁是它做不了什么。

**四篇加起来，画的是一条线：这一侧交给 AI，那一侧必须确定。**

而门禁这件事真正教的，就是这条线该按什么画。

不是按「难不难」画，也不是按「重不重要」画。**是按「能不能接受它偶尔出错」画。**

Agent 擅长的是「多数情况下做对」。门禁要的是「一次都不能错」。**这是两种性质不同的东西，所以不能放在同一侧。**

落到一条可问的话：**这一条，你能接受它十次里错一次吗？**

- 能——交给它，然后用[第 10 篇那套日志](https://blog.yingtongxue.cn/#/blog/2026-09-17-agent-10-logs-and-versions)在事后查得到。
- 不能——挪到确定性那一侧，也就是这一篇讲的那个「它够不着的地方」。

所以逐条问。**问出来是第二类的那几条，才值得你花力气真的把门修在外面**，而不是给每一条都写一句「不许」。

## 七、下一篇讲什么

线画好之后，还剩一类情况没处理——**线上的事它做得了，可它不该做。**

比如：它不确定，但照样给了答案；它翻遍了知识库，那件事根本没写；它发现两份文件说法打架；它调的工具返回了错误；它发现自己权限不够。

这几种情况下，最糟糕的选择是**猜一个继续往下走**——而那恰恰是模型最擅长的事。

第 15 篇讲异常路径：模型不确定、知识缺失、权限不足、工具失败、结果冲突，五种情况各自该怎么停、停下来之后找谁。
