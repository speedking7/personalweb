到第 11 篇为止，你一行代码都没写。

建空间、传知识文件、写系统提示词、建任务、点立即执行、建目录、写索引——全是点出来的。手上那个 Agent 能查制度、答案里带得出可追回原文的锚点、做过的事留得下痕迹。

**它已经能干活了。**

那么线在哪儿？

这一篇画那条线。但真正要讲的不是「哪几处点不出来」，而是一件更容易答错的事：**那三处卡点的性质完全不同，而多数人把它们当成了同一种。**

## 学习目标

| | 你能做到 |
|---|---|
| 一 | 说清无代码走到哪儿为止，以及你已经走完了多少 |
| 二 | 认出三处卡点，并说清每一处该怎么办 |
| 三 | 判断自己手上这个需求要不要找工程搭档，还是该去找别人 |
| 四 | 说清为什么「三层状态全绿」不等于功能可用 |
| 五 | 写出一份能递给工程搭档的需求说明 |

产出物是一张判断表，加一份需求说明。

**这一篇的材料来自两处**。一处是演示空间，就是跟着前十一篇搭的那个；另一处是另一个项目——它把这个平台的插件、技能、外部接入挨个试了一遍，撞出来的东西演示空间碰不到。**凡是演示空间碰不到的，都出自后者，文中会写明。**

## 一、无代码走得比你以为的远

先把已经走完的路摆出来，因为多数人会低估这一段。

| 点得出来的 | 你在哪一篇做过 |
|---|---|
| 建工作空间 | 01 |
| 把一批文件变成知识库 | 01、11 |
| 写系统提示词，定它是谁、按什么规矩办事 | 01 |
| 建任务、指派执行者、点立即执行 | 04 |
| 建目录、写两级索引、填元信息 | 11 |

**这一套点下来，你得到的是一个能干活的问答型 Agent**。不是玩具，是真能接活的那种——前提是知识库还没越过[第 11 篇那个拐点](https://blog.yingtongxue.cn/#/blog/2026-09-18-agent-11-knowledge-base)。

所以「无代码只能做个 demo」这个印象是错的。**它的边界不在功能复杂度上**——一个查制度的 Agent 要跨文件推理、要摆出可追的依据、要留下可查的记录，这些听起来都复杂，而它们全在线内。

**线不在那儿。**

### 有一项要单独说：审查那一档不是默认就在的

任务是有「待审查」这一档的。但[第 04 篇在演示空间里跑过一次](https://blog.yingtongxue.cn/#/blog/2026-09-09-agent-04-approve-the-list)：建任务、执行者设成 Bot、点立即执行，**它执行完直接停在「已完成」**，中间没有任何审查环节，界面也没有任何提示说少了一步。

所以别事先把这一档算进你已经点出来的清单——**它在不在，只能跑一次看它停在哪儿**。这件事到第五节还要再碰一次。

## 二、三处卡点，性质完全不同

| 卡点 | 卡的是什么 | 你多半会错在哪儿 |
|---|---|---|
| 一 · 打包与注册 | 让 Agent 用上一个你们自己的能力 | 以为自己搞得定 |
| 二 · 验证 | 判断某一步到底成没成 | **不知道有这一步** |
| 三 · 约束 | 让它不做某件事 | **以为做完了，其实没做** |

**三处里只有一处一定要找人**。这是这一篇最要紧的一句。

**第一处**要找，因为那是一件确实做不了的事。**第二处根本不用找**——那是一项自己能学会的手艺，多数人只是不知道有这回事。**第三处看情况**，而且多数情况下也不用找：得先认清那条约束压根没被执行，再看它要不要「拦」，才轮得到讨论找谁。

把三处都当成「要找人」，你会在后两处白等资源。把三处都当成「我能搞定」，你会在第一处和第三处带着一个看起来正常、实际残废的 Agent 上线。

## 三、卡点一 · 打包与注册：你做不了，要找人

什么时候会撞上它？**当你想让 Agent 用上一个平台没有、而你们自己有的能力**。比如去你们的单据系统查一张单的状态、调一个内部的计算服务、读一个只有你们才有的数据源。

知识库解决不了这个——知识库放的是「事实是什么」，不是「去做一件事」。

这种能力要变成 Agent 调得动的东西，中间有两步：**打包**，把它按平台规定的格式封成一个制品；**注册**，把制品交给平台解析，再绑到某个 Agent 身上。

打包要写文件，这一步你做不了。**而没有包，注册这一步无从谈起**——所以整段一起卡住。

### 打包里有一个坑，值得你知道

不是要你去打包，是因为**这个坑决定了下一节为什么重要**。

那个制品是个压缩包，**包的结构有讲究**——另一个项目里弄错过一次，解析出来是零个组件。

而同一个项目量到的另一半是：**一个组件为零的包，照样能「已发布」、照样绑得上 Agent。**

记住这条链：**包结构错 → 组件为零 → 而它一路绿灯。**

顺带一句排资源的话：**打包交付的是一个制品，不是一项长期工作**。你要的可能只是请人帮忙打一次包，不是长期占着一个工程搭档。

### 跟工程搭档说什么

你不需要懂打包怎么写。你需要说清楚的是这四样：

| 要说清的 | 例子 |
|---|---|
| 这个能力做什么 | 按单号查一张变更单的当前状态与各节点时间 |
| 输入什么，输出什么 | 入参：单号。出参：状态、各节点时间、当前处理人 |
| 它能不能改东西 | **只读。不允许任何写操作** |
| 怎么算做成了 | **由你定验收，不由他定** |

第三行是你的活不是他的活——[第 08 篇那张权限矩阵就是填这一行的](https://blog.yingtongxue.cn/#/blog/2026-09-15-agent-08-tool-whitelist)，工程搭档不知道你们业务上哪些字段碰不得。

最后一行最容易漏。没有它，交付标准就是「代码跑通了」——而下一节会告诉你，跑通跟能用是两回事。

## 四、卡点二 · 验证：你做得了，但你不知道要做

这一处最该花时间，因为它是三处里唯一一处**你自己就能搞定、而多数人根本不知道存在**的。

先看实测。另一个项目里给一个 Bot 装自定义技能，装完之后三项状态是这样的：

| 检查点 | 显示 |
|---|---|
| 插件状态 | 已发布 |
| Bot 绑定 | 已启用 |
| 上传过程 | 零报错 |

**三项全绿，而功能是零**——平台侧同期返回的是「未知技能」，组件列表是空的。

**而且同一时间，Bot 自己还在说「四个 Skill 均已成功触发」。**

这不是偶发。同一个平台上还量到过一次同形的：把外部服务按两种标准配置接进来，两种都解析成功、绑定成功，**而 Bot 的工具集里一次调用都没有**。

### 为什么会这样

因为这几个状态量的是不同的东西，而它们长得一样。

| 状态 | 它真正证明了什么 | 它没证明什么 |
|---|---|---|
| 已发布 | 这个制品在平台上存在 | 它里面有东西 |
| 已绑定 | 这个 Agent 与这个制品建立了关联 | 关联的东西能用 |
| 上传零报错 | 文件传输完成了 | 平台解析出了内容 |
| Bot 说成功了 | **什么都没证明** | —— |

**每一层都不能替代下一层**。一个组件为零的包，照样能「已发布」、照样能被绑定。

最后一行要单独记。[第 10 篇讲过日志里有三类东西](https://blog.yingtongxue.cn/#/blog/2026-09-17-agent-10-logs-and-versions)，Bot 说的话属于「生成」那一类——它一定有，但可能假。**拿它当验证依据，等于让被检查的一方出具检查报告。**

所以立一条规矩，它不只管注册，管这个平台上一切写操作：

> **任何写操作的成败，一律以回读目标资源判定，不采信操作后的成功提示。**

它跟[第 04 篇那条「Agent 的自我报告一概不采信」](https://blog.yingtongxue.cn/#/blog/2026-09-09-agent-04-approve-the-list)是同一条原则的两面：**一个说别信 Agent 说的，一个说别信平台说的。判据只有一种——自己回去看。**

### 回读什么

方法层的答案是一句话：**去平台记录工具调用的地方，找那一次调用**。换个平台，要问的是同一个问题——这个平台把工具调用记在哪儿。

在 knodo 上，你已经做过这个动作很多次了：第 01 篇看它读了哪几份文件、第 11 篇看它这一次读了几份、第 10 篇拿它区分「系统记的」和「模型说的」。

做法是：**给它一道用得上这个能力的题，然后去轨迹里找那一次调用。**

| 轨迹里 | 结论 |
|---|---|
| 有调用记录，有返回 | 成了 |
| 有调用记录，返回是错误 | 注册成了，能力本身有问题——**这时候才该回去找工程搭档** |
| 一条调用记录都没有 | **换两道题再跑。三次都没有，就当它没装上，回去查包** |

第三行为什么要跑三次？因为[第 11 篇那条判据在这儿同样成立](https://blog.yingtongxue.cn/#/blog/2026-09-18-agent-11-knowledge-base)——**单次观察什么都判不了**。题出得不巧，它这一次没用上，你会误判成「没装上」。

**这一处不需要工程搭档**。需要的是知道有这回事，以及知道去哪看。

## 五、卡点三 · 约束：你以为你做了，其实没做

第三处最隐蔽，因为它没有任何症状。

你在系统提示词里写下「不许做某件事」，保存，界面显示成功。**这一步确实完成了**——提示词里确实有那句话。

问题是它不一定起作用。

[第 11 篇已经用过这条实测](https://blog.yingtongxue.cn/#/blog/2026-09-18-agent-11-knowledge-base)：另一个项目里给 Bot 划好了扫描范围，它照样用 shell 读了范围外的文件。结论是那一条：

> **提示词能规定「做什么」，规定不了「不做什么」。**

所以凡是「不希望它做」的事，提示词这条路走不通。

**但走不通不等于要写代码**。[第 07 篇那张矩阵早就分过了](https://blog.yingtongxue.cn/#/blog/2026-09-14-agent-07-action-layers)：前三层那些不许做的，出路是**换动作、换下游、把知识库收窄**——这三条全是点得出来的。真要在动作发生那一刻把它拦住，才落到代码级门禁或者结构上的够不着，那两样在无代码之外。

回头看，这件事在前面几篇留下过痕迹，而它们的出路并不相同：

| 在哪篇 | 什么形态 | 出路 |
|---|---|---|
| 08 | 「不得替提单人给出风险等级结论」——字段权限拦不住，因为风险等级根本不是提单要素里的一格 | 换动作：把「它判」改成「它把判据摆出来，人判」 |
| 11 | 检索预算写在操作规则里，管不住它真读几份 | 当尺子用，看轨迹核偏离 |
| 11 | 废止之后那条「对外回答只用 `03`」，同样管不住 | 改那份文件本身，让它读到正确的东西 |

**这三条的共同点是：约束写下来了，而执行约束的东西不存在**。而三条的出路里，一条要写代码的都没有——**先别急着去排工程资源，先看这一条到底要不要「拦」。**

第一节末尾那个「审查那一档不是默认就在的」，是同一件事的另一种形态——**你以为链路上有一道关，实际那道关没有被接上。**

第 14 篇整篇讲这件事。这一篇只钉一条：**判断一条约束成不成立，先问它由谁执行。答案是「提示词」的，就是没执行。**

## 六、判断自己要不要找搭档

把你手上那个需求的每一行填掉：

| 问 | 你的答案 | 要是「是」，去找谁 |
|---|---|---|
| 它要用一个平台没有、你们自己才有的能力吗 | | 工程搭档，走第三节 |
| 它要往别的系统里写东西吗 | | 工程搭档，但先看第 13 篇 |
| 它有「绝对不能做」的事吗 | | **先回第 07 篇那张矩阵看它在第几层**——前三层换动作就够，四层往后才轮到门禁 |
| 它要用的东西，你的账号看不见吗 | | **管权限的人，不是工程搭档** |

**四行全是否——那就自己搭，前十一篇够用了。**

第四行要单独说，因为它最容易被误判进第一类。你的账号能看见的空间数，可能远小于组织实有的。**这时候你缺的不是人手，是授权**，去找一个工程搭档只会一起卡住。

还有一条判据，是[第 07 篇那套动作分层留下的](https://blog.yingtongxue.cn/#/blog/2026-09-14-agent-07-action-layers)：**能不能设计出某个控制点，先看目标系统有没有对应的状态**。演示制度里没有草稿态，所以「它建、人审、再提」这条路根本设计不出来——那不是工程能力问题，再多的搭档也做不出来。

**前三行里有任何一行是是**，你要做的不是等资源，是**先把需求说明写出来再去找人**。理由很实际：工程搭档的时间通常比你紧，你带着一份写清楚的东西去，和带着一句「我想做个 Agent」去，拿到的排期不一样。

需求说明写什么，就是第三节那四行：做什么、入参出参、能不能改东西、怎么算做成了。**全是他不知道而你知道的。**

（那四行写的是「一个能力」。要是找人做的是门禁，换一份写法：**写清哪些事绝对不许发生，以及你打算拿什么证据说它被挡住了。**）

## 七、下一篇讲什么

这一篇的第一处卡点里跳过了一件事：你想调的那个系统，**未必已经有接口可调。**

前面一直假设「去单据系统查一张单」这件事是做得到的，只是要打包。但现实里更常见的是：那个系统压根没开放接口，或者有接口但你申请不到权限，或者接口在而没人维护、坏了找不到人。

**这部分的工作量经常超过搭 Agent 本身，而它恰好是业务顾问的强项**——盘点、谈权限、写需求、约定责任人，这些事很难指望工程搭档代劳，因为要跟人打交道。

第 13 篇讲外部系统接入：怎么盘点现在能调什么、怎么分清「拿不到」是权限问题还是压根没接口、以及接口真做不出来的时候有哪几条退路，各自的代价是什么。
