# SOMP 业务流程与可 Agent 化分析

> 来源：2026-09 通读 `/home/speedking/projects/SOMP`（1.1G / 14920 文件，重点读 docs/bizdocs、
> current-implementation-status、self-hosting-runbook、flows/execution.py）产出。
> 用途：AI Agent 实战系列第七部分（多 Agent）的案例底稿。

## 一、它解决什么业务问题（无技术名词版）

一个团队同时维护好几套已上线的系统。用户报了毛病、或业务方提了新要求，原路径是：
有人先判断这算不算毛病、影响多大，然后排期、找人改、写测试、互相看代码、发到测试环境、
请提需求的人来验、验完合并、挑时间上线、上线后盯着。每一步都要人推一下，人一忙就卡住，
链条上任何一环漏掉（没补测试、没人验收就上线）事后才发现。

SOMP 把这条链子变成自动运转的流水线：接单后自动判断、自动改、自动验证、自动部署到测试环境，
**只在真正需要人拍板的地方停下来发通知等人点确认**，人点完继续跑。
人从「每一步都要动手」变成「只在几个关口做决定」。

## 二、完整流程

两条流**后半段完全共用**，只有前段不同。

**Bug flow 前段**：入库编号 → is_bug 判定（置信度 <70% 转人工）→ 影响分析出 risk_level
→ 风险路由（LOW/MEDIUM 通知继续，**HIGH 停下等 BO 批**）→ 可选拆解 + 拆解审批（人工）

**Feature flow 前段**：入库 → **BO 立项审批（停）** → 深挖访谈提问 → **BO 答 6 题（停）**
→ 合成需求文档 → **BO 确认（停）** → CEO 视角评审框架 → **BO 填业务方向（停）** → 合成 CEO 报告
→ **BO 确认（停）** → 架构分析底稿 → **Tech Reviewer 填架构决策（停）** → 合成工程评审报告
→ 规划门禁校验（四份制品非草稿才放行）→ UI 原型生成 → **BO 确认原型（停）**
→ 拆解 + **BO 确认拆分方案（停）**

**共用执行段**：选适配器 → 建工作分支/worktree → agent 编码 → 提交 → 集成检查 → TDD → 代码评审
（三道自动门，各有人工裁决兜底）→ 部署 dev + smoke（失败先自愈重试）→ 部署 staging（FIFO 排队）
→ 可选 E2E → QA 报告 → **UAT 等提交者验收（停）** → 合并 → 写入生产发布队列 → 关闭为 queued_for_release

**终点不在任务流里**：生产部署是**独立的、人在发布管理页触发**的批次动作。

## 三、四个角色

| 角色 | 干什么 | 出现在哪 |
|---|---|---|
| user / 提交者 | 提交 bug/需求；在 staging 做 UAT 验收 | 入口、UAT |
| bo 业务负责人 | **只管业务价值和优先级，不做技术决策** | Feature 前段几乎所有门 + Bug 高风险门 |
| architect | 技术方案与架构影响；所有质量门的人工裁决兜底；发布管理 | 规划中段 + 质量门 + 发布 |
| admin | 平台级：系统接入、用户与角色、配置 | 流程之外 |

实现细节：全局角色实际只分 member/admin，bo/architect 是**按系统授权**的。

## 四、质量闸门在卡什么

- **integration check**：只在 diff 碰到 API 面时触发，卡「是否破坏已有接口契约」。**有人工兜底**
- **TDD**：卡两条硬线——测试 100% 通过（不可配置）；**变更文件**行覆盖率 ≥ 阈值（默认 80%）。
  空变更文件列表直接判失败。**无兜底，纯硬门**，失败回流 agent 重做
- **code review**：卡 Critical = 0。**有人工兜底**——评审要求改但 agent 没产生任何改动时升级为裁决门
- **smoke**：部署**前**用 worktree 现场构建镜像跑冒烟，卡「这版起得来吗」。失败先回灌 agent 自愈，
  耗尽后转人工
- **UAT**：卡「业务上真修好了吗」，人在 staging 实测。最多 3 次拒绝后升级 BO
- **canary**：**当前是确定性 MVP 制品**，活的监控回路还没接
- 另有 E2E（默认关）、lint gate（选配）、**预算熔断**（agent 调用次数超限 → 人工裁决是否续命）

## 五、哪些环节本质是「一个 agent 在干活」

| 环节 | 输入 | 输出 | 失败/不确定怎么办 |
|---|---|---|---|
| is_bug 判定 | 描述、stack trace、只读代码库、文档检索、历史 lessons | is_bug / confidence / evidence | <70% 或文档索引为空 → 转人工；48h 无响应关闭 |
| 影响分析 | 描述 + IsBugResult + 代码库 | risk_level、affected_files、change_summary | 字段缺失即 gate 失败 |
| 拆解判断 | 任务描述 + 影响面 | 子任务清单与边界 | 必须过人工审批门；**已知过度拆分是真实痛点** |
| 规划三件套 | 需求原文 + 人的回答 | 访谈文档 / CEO 报告 / 工程评审报告 | 分「提问模式」和「合成模式」两轮：**agent 只负责问对问题和把人的答案合成文档** |
| UI 原型生成 | 已批准的需求文档 | 可在 iframe 里看的 HTML 原型 | BO 不满意打回；批准后注入编码 agent 的 prompt |
| **编码 agent** | 任务描述 + 影响分析 + 已批准方案 + 原型 + 代码上下文 + lessons | 工作区里的真实文件改动（**平台事后用 git diff 提取，不信 agent 自报**） | 重试 3 次退避；**失败绝不自动切换框架**；超预算熔断 |
| 集成检查 | 脱敏后的 git diff | verdict + 理由 | 外部评审关闭时 **fail-closed** |
| 代码评审 | BASE/HEAD 之间的 diff | verdict/comments | CHANGES_REQUIRED 但 agent 没改动 → 升级人工裁决 |
| 部署失败自愈 | 部署/smoke 错误输出 | 修复 diff | 先由**正则**分类 code/infra，**只有 code 类才交给 agent**；infra 类直接转人工 |
| E2E triage | Playwright 失败报告 | 失败归因 | 归因不明 → 人工裁决 |
| 文档同步提案 | 完整 diff + 文档树 | 哪些文档过时 + 逐段替换草稿 | **应用提案刻意保持手动**，不自动 commit |
| 经验蒸馏 | 已完成任务的过程 | 短条目（category + 触发场景 + 教训），可检索 | 自动条目按 task_id 去重防重放污染 |

**三处名义上是 agent、实为确定性桩**（教学时要说清）：QA 报告、canary 报告、原型的 smoke 证据。

## 六、哪些靠确定性工程设施

**这条线划得很清楚：凡是「必须每次都一样」的事，一律不交给 agent。**

1. 流程编排与断点续跑（checkpoint + interrupt/resume）。**所有人工门都是「图停在这里」，
   不是「agent 在轮询等待」**
2. 分支与工作区隔离：每任务一条分支 + 独立 worktree；子任务在集成分支汇合
3. 仓库并发锁：所有基仓 git 操作串行化
4. 发布队列与锁：staging FIFO 排队 + 行锁；生产走队列 + 批次 + **release-id 一致性 guard**
5. **超时守卫**：独立扫描过期审批。UAT 超时自动批准并 resume；高风险 BO 门超时 → 关闭（**不自动继续**）
6. **质量度量的独立执行**：平台自己跑 pytest --cov、自己算覆盖率、自己 docker build 跑 smoke。
   **agent 的自我报告一律不采信**
7. 失败分类：正则规则集分 code/infra，决定「回给 agent」还是「叫人」
8. 成本熔断：按任务的 agent 调用次数上限
9. 回滚与降级
10. 身份与安全：RBAC、一次性审批 token、webhook HMAC、命令串注入防护、diff 送 LLM 前脱敏
11. 任务编号与制品存储：每步产出结构化 Artifact，由 Gate Script 校验格式完整性
12. 部署 provider 接缝
13. 孤儿任务对账

## 七、在另一个平台重建的最小可用版本（依赖顺序）

**注意 agent 到第 4 步才出场，前三步全是确定性设施。**

1. 任务入库 + 编号 + 状态机——没有这个，后面一切没有挂载点
2. **可持久化的流程编排，支持在任意节点停下并按外部事件恢复**——这是地基，也最容易低估。
   先跑通「停下—发通知—人点击—继续」的空回路，再往里填内容
3. 代码工作区隔离：一条任务分支 + 独立 worktree + 仓库串行锁
4. 调用编码 agent + **平台用 git diff 提取结果**（含空 diff 判失败）
5. **平台独立执行的 TDD 门禁**，失败回流 agent。这是第一道真门，
   也是「不信 agent 自报」这条原则的落地点
6. 部署到可访问环境 + 部署前 smoke
7. UAT 人工审批门 + 通知 + 一次性 token——到这里就是一条能用的闭环
8. 合并 + 发布队列 + 人工触发的生产发布
9. **超时守卫**——有了人工门就必须有它，否则流程会永久悬停
10. 加 LLM 质量门并同时配人工裁决兜底

以上是 MVP。之后才谈影响分析、规划评审链、UI 原型门、拆解、E2E、canary、文档同步、经验蒸馏。

## 八、最值钱的踩坑与反直觉结论

1. **别自动批人工门。**跑到门口、给足证据、然后停住
2. **dogfood 是最大的 bug 发现机制。**SOMP 把自己注册为自己的托管系统
3. **自部署的 bootstrap trap**：部署自己的后端会重启正在执行部署的编排器（自杀），
   且只重建前端会导致新前端跑在旧后端上。解法是返回 awaiting_manual 踢到宿主机原子执行。
   **任何「平台维护自己」的教学案例都会撞上这个**
4. **覆盖率只算变更文件，阈值 80% 不是 100%。**理由明确：追求 100% 会催生只为刷分的无意义测试
5. **不信任 agent 的自我报告。**覆盖率平台自己跑，diff 平台自己从 git 提取
6. **agent 失败不自动换框架。**adapter 失败 3 次直接 FAILED，避免「换个模型再试试」掩盖真问题
7. **自动拆解会过度拆分。**真实案例：一个文档生成的修复被拆成 5 个**串行**子任务，
   5 倍门禁开销、零并行收益。拆解门缺「值不值得拆」的启发式
8. **纯「分析」型子任务是反模式。**唯一产出是一份草稿 md，污染仓库又引发门禁连环摩擦
9. **子任务并行的瓶颈是环境不是调度**（共享 dev/staging 栈、单条集成分支、仓库锁）
10. 「低置信度事件链」最终判 WONTFIX——阈值路由已覆盖，专门机制是过度设计
11. **门禁默认方向是 fail-closed。**外部 LLM 评审未开启时是拦住而不是放行
12. **审批状态的真相在 UI 不在邮件。**SMTP 没配好时邮件只进队列
13. 两个真实的「门禁形同虚设」缺陷（好反面教材）：环境评审通过后曾错误**跳过** TDD；
    任务详情曾优先展示**旧的通过记录**而掩盖最新失败
14. 辅助 LLM 要跟随系统选定的适配器，不要硬编码某厂商
15. `SOMP-BUG-XXXX` 是运行态任务数据，不是代码缺陷——自托管系统里两者极易混淆
