## 一、这套东西解决什么问题

**适用前提（站主原话的意思）**：不引用外部 RAG 知识库、不使用知识图谱等服务时，
**仅通过目录与索引文件结构的设计**来提升知识使用效率和准确率。

换了前提就换一套。**它是一类调优手段，不是标准答案**——这一条写文章时必须说在前面。

## 二、目录分层

根目录五个编号目录加若干根文件：

```
01-general/      通用
02-source/       受控证据（原始资料，不可变）
03-knowledge/    已发布知识（对外回答只用这里）
04-operations/   运行：草稿、日志、维护任务
90-system/       机器治理：模板状态、发布清单
START-HERE.md    入口
AGENTS.md        操作规则
```

**编号是刻意的**：它同时表达顺序与层级，而且让「先看哪个」这件事不依赖命名的语义理解。

## 三、两级索引，索引只做导航

`03-knowledge/INDEX.md` 是根索引，指向模块索引（如「标准规范」「流程指南」），
模块索引再指向具体主题文件。索引文件自身带 frontmatter：
`type` / `title` / `description` / `owner` / `status`。

**索引里明写一条约束**（大意）：**用主题文件回答问题，不要把这份索引当业务依据引用。**

这一条防的是模型拿目录里那句摘要当答案——正好对着我们实测到的「出处错」的上游。

模块索引里另有一句：**在这里加稳定的主题文件，索引保持只做导航。**
也就是**规则写在主题文件，索引不承载规则**。

## 四、检索预算 —— 这套设计的核心

`AGENTS.md` 里单列一节，大意是：

> 根索引 → 一个模块索引 → 最多两份主题文件。
> 命中已核实的知识之后，不再扫运行区、系统区与原始证据。

**这是渐进式披露的工程形态。**目录、索引、元信息都是手段，
**给检索定一个上限**才是目标——手段可以换，这个概念换不掉。

它直接对着我们实测的那个现象：知识库小的时候模型全量读进上下文，
大到读不动之后就要靠地图来定位。

## 五、答案契约（六条，大意）

1. 回答前先读根索引
2. 只用状态为 active 的知识
3. 引用精确的主题路径与来源定位
4. 适用条件可能改变答案时，先反问
5. **遇到同等具体的冲突陈述就停下**
6. **证据不足时记一次 miss**

第 5、6 条正是第 15 篇「五种必须停下来的情况」里的**结果冲突**与**知识缺失**，
只不过在这里已经是可执行的契约条款。

## 六、变更契约（六条，大意）

1. **绝不臆造负责人、评审人、来源、版本或审批**
2. 原始证据保持不可变、可追溯
3. 索引保持导航性，规则放主题文件
4. 经来源核验与审批之后才发布
5. **approved 在发布动作成功之前仍算草稿状态**
6. 关闭维护周期前，先验证线上检索确实生效

第 1 条直接对着编造出处。第 5 条那个「approved 仍算草稿」很精妙——
它承认「批准了」和「生效了」是两件事，正好呼应第 09 篇批准与执行的一致性。

## 七、生命周期状态机

```
draft → source_verified → review → approved → published → validated → closed
```

七个状态。**`source_verified` 单独成一档**，说明「来源核验」被当成一道独立门禁，
而不是审批的一部分。

## 八、代价（站主明确要求必须同时讲）

- 知识库的**设计复杂度**上升
- 每次维护知识，要同时保证**目录结构、索引内容、元信息三者一致**
- **漏一处，地图就和地形对不上，模型会被稳定地引到错的地方**，而这种错比没有地图更难发现

**一致性怎么维持，本篇不预设答案。**手段有人工评审、脚本校验、发布前清单、
专门技能、独立的治理 Agent……**用 Agent 治理也只是其中一种**，
要看知识规模与变更频率再定。第 11 篇要做的是把代价讲清楚，让读者自己算账。

## 九、写第 11 篇时的两条纪律

**其一，先让读者碰到问题再给设计。**读者读到第 11 篇时，
手里应该已经有一个真的变慢变糊的库了——第 02 篇末尾给的那四条症状
（答漏、时对时不对、变慢变贵、掺进不相干内容）就是入口。
**在他吃过这个亏之前把整套方案端出来，他学不会为什么要这么做。**

**其二，说清这只是一类手段。**换个前提（上外部检索服务、上知识图谱、
知识类型含图片音视频）整套设计都不一样。
