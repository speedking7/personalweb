## 零、这一遍与清单的三处偏差（先说边界，再看结论）

清单假设的是**人在界面上点**。这一遍走的是 REST API。**凡是「界面长什么样」的问题，这一遍一律没回答**，
第六节那九项 ⬜ 基本原样留着。能回答的是另一类问题：**它到底怎么找知识、答得准不准、
在知识缺失时是承认还是编**——这些不因入口不同而改变，而它们正是第 01、02 两篇的正文。

| # | 偏差 | 影响 |
|---|---|---|
| 1 | 用 API 建空间 / 传文件 / 建 Bot，没有点过一次界面 | 六张截图一张都没拍；九项 ⬜ 只解掉两项 |
| 2 | 五道题**各自独立开一个会话**，不是清单说的「一个对话里一题一题问」 | 见下方「为什么改」 |
| 3 | 顺手加跑了一个清单里没有的探针（索引延迟） | 结论推翻了清单的一条常见错误，见第三节 |

**第 2 条为什么改。** 原计划在同一个会话里连问五题，第 2 题就撞上平台故障：
`AGENT_STREAM_DISCONNECTED`，挂了 **542 秒**后断流，整个会话状态转 `error`，后面三题没法接着问。
改成一题一个会话之后，Q2–Q5 首次尝试全部成功。

这次故障本身要记两笔：

- 🟢 **平台会在无征兆的情况下断流**，且失败前会先静默挂九分钟。第 15 篇「工具失败」与第 20 篇
  「退出机制」有了第一个真实样本。
- 🟢 **判定纪律没白立**：轮询把它判成 `failed`（已确认失败），而不是 `poll_exhausted`（等不下去了）。
  两者混为一谈的话，这一条会被记成「超时」，而超时是不能拿来判定 Bot 表现的。

**一题一会话反而更干净**：题目之间不会互相带上下文，第 5 题的「我提的这个需求」没有前文可指，
反问的成色更足。

## 二、五道验收题：原问原答

以下回答**一字未改**，由脚本从会话消息直接装配，不是转述。

### 第 1 题

| | |
|---|---|
| **原问** | 提单之后多久会有人处理？ |
| 清单预期 | 答得出（受理 1 个工作日） |
| 测的是什么 | 单文件直答，基线 |
| **实测结论** | ✅ 符合预期 |


**原答**：

```text
根据流程文件，分两种理解回答您：

## 1. 提单后多久有人接手（受理）

**1 个工作日**。提单后单据进入「待受理」，由**系统管理员**在 1 个工作日内转入「分析中」。
> 依据：《提单与验收流程》第四条「各节点时限」表第一行。

⚠️ 前提是提单要素齐全：所属系统、变更类型、现象/需求描述、期望结果、期望完成时间、联系人，**缺一不予受理**；缺陷修复还须附复现步骤、发生时间、影响范围。
> 依据：《提单与验收流程》第二条。

## 2. 多久真正进入「处理中」——取决于风险等级

后续时限因变更风险等级不同而不同（按《变更风险分级表》判级，命中多条按最高等级）：

| 环节 | 时限 | 依据 |
|---|---|---|
| 分析中 → 待审批/处理中 | 3 个工作日 | 《提单与验收流程》第四条 |
| **低风险**：不经过待审批，分析完直接进入处理中 | — | 《提单与验收流程》第三条；《管理办法》第三条（低风险无需审批） |
| **中/高风险**：待审批 → 处理中 | 审批人 2 个工作日内响应，超时视为退回 | 《管理办法》第三条；《提单与验收流程》第四条 |

即粗略估算：**低风险约 4 个工作日**进入处理中（1+3），**中/高风险约 6 个工作日**（1+3+2）。

## 3. 两点提醒

- 任一节点被**退回**的，时限从重新提交之日起**重新计算**（《提单与验收流程》第四条）。
- 紧急修复可先处理后补审，但须在恢复后 24 小时内补齐提单与审批记录（《管理办法》第二条）。

以上时限为流程规定，实际处理进度与上线时间不作承诺。如果您告诉我这次变更的具体内容或风险等级，我可以帮您对照《变更风险分级表》判断适用哪一档。
```

### 第 2 题

| | |
|---|---|
| **原问** | 验收不通过会怎么样？ |
| 清单预期 | 答得出（退回写明不符之处，时限重算，连续 3 次升级） |
| 测的是什么 | 单文件直答，换一份文件 |
| **实测结论** | ✅ 符合预期 |


**原答**：

```text
根据知识库文件，验收不通过后的处理如下：

**1. 退回时须写明具体不符之处**
验收不通过的，须在退回时写明**具体不符之处**；只写「不行」「有问题」的退回无效，系统会要求补充说明。
> 依据：《提单与验收流程》第五条

**2. 单据状态转为「已退回」**
状态流转中，「待验收」节点不通过会流向「已退回」，修改后重新提交。
> 依据：《提单与验收流程》第三条

**3. 时限重新计算**
任一节点退回的，时限从重新提交之日起**重新计算**。
> 依据：《提单与验收流程》第四条

**4. 连续 3 次不通过会自动升级**
同一张单**连续 3 次验收不通过**的，自动升级至业务负责人，由业务负责人决定继续修改、重新立项或关闭。
> 依据：《提单与验收流程》第五条

**补充提醒（与之相关但性质不同）：**
- 验收时限是提单人 **5 个工作日**；逾期未完成验收的，系统视为**默认通过**并自动关闭，后续如有异议须另行提单。
> 依据：《提单与验收流程》第四条
- 另外《管理办法》第五条规定「同一变更在 30 日内第三次被退回，须先经业务负责人重新立项」——但文件里未写明这里的「退回」是否包含验收环节退回，建议向研发管理办公室确认口径。
> 依据：《研发变更管理办法》第五条

另外需要注意：验收内容只包括「提单里写的期望结果是否达成」，以提单未写明的新要求作为不通过理由，属于常见退回原因中的无效情形。
> 依据：《提单与验收流程》第五条、第六条
```

**结论：属于高风险变更，由架构负责人审批，且业务负责人会签。**

分档确认（按规则先定档，再给结论）：

1. **为什么是高风险**：支付回调属于「资金链路：支付」，分级表高风险第一条命中即成立。

| 项目 | 要求 | 依据 |
|---|---|---|
| 审批人 | 架构负责人审批 + 业务负责人会签 | 《研发变更管理办法》第三条审批表·高风险行 |
| 必须附带材料 | 影响范围说明、**回滚方案**、验证方案 | 同上 |
| 不予受理情形 | 高风险未附回滚方案，直接不予受理 | 《研发变更管理办法》第五条第 2 项 |
| 上线窗口 | 只能安排在每周二、周四的变更窗口 | 《研发变更管理办法》第四条 |
| 审批时限 | 审批人应在收到请求后 2 个工作日内响应，超时视为退回 | 《研发变更管理办法》第三条 |

**一个例外**：如果这次改动其实不触及资金处理逻辑（比如只加日志埋点、不改对外行为），那可能落在低/中风险档——但分级表明确「不因为只改一点点而降级」，是否命中「资金链路」需要以实际改动内容判断，这条我建议你提交时由分析人认定，或直接咨询研发管理办公室。

另提醒：审批结果与上线时间我无法代审批人承诺，需以单据流转为准。
```

## 三、清单与操作说明需要更正的地方（🟢 全部本次实测）

### 三之零 · 工作指引在 Bot 对话里确实不生效（🟡 文档推断 → 🟢 实测确认）

操作说明零之一那条「全篇最重要的一条」原本是从官方 FAQ 推的。**本次实测确认成立。**

做法：往空间的工作指引里追加一句不可能被误认的标记指令——「每次回答的第一行必须原样输出
`GUIDELINE-ACTIVE-7731`」——然后用同一个问题（「提单要素有哪些？」）问两次，只改一个变量：

| 提问方式 | 标记是否出现 | 结论 |
|---|---|---|
| `chat/submit` **传 `botId`**（= 界面上选中助手后聊） | ❌ 未出现 | 工作指引**不生效**，走的是 Bot 的系统提示词 |
| `chat/submit` **省略 `botId`**（= 界面上不选助手直接聊） | ✅ 出现，且在第一行 | 工作指引**生效** |

两次回答都正确引用了《提单与验收流程》第二条，**说明知识库两边共享**——
FAQ 那句「两者共享同一个空间的知识库与 Skill，区别只在 System Prompt 的来源」也一并坐实。

**证据边界**：本次验证的是 **API 层 `botId` 传与不传**的差别。界面上「选中助手」这个动作
是否精确等价于传 `botId`，🔴 推导极可能是，但没有登录核过。写文章时这条可以按 🟢 用，
只是别把它说成「界面实测」。

探针用后已恢复原工作指引并回读比对一致，两个探针会话已删除。

### 三之一 · 第 3 题的预期被推翻，但**原因不是平台检索强，是知识库太小**

「架构负责人审批 + 业务负责人会签 + 回滚方案」，两跳一次做对，还顺带引用了
「命中多条按最高等级」那条说明。

**但工具轨迹说明它根本没做检索：**

           → /workspace/变更风险分级表.md
             /workspace/提单与验收流程.md
             /workspace/研发变更管理办法.md
[1] Read   /workspace/研发变更管理办法.md      ← 整篇
[2] Read   /workspace/变更风险分级表.md        ← 整篇
[3] Read   /workspace/提单与验收流程.md        ← 整篇
```

**它把整个知识库读进了上下文。**三份文件合计 2.6 KB，全量装载比检索便宜得多，
所谓「两跳」在它眼里根本不是两跳——两条依据都在同一份上下文里。

于是事实清单那条论断**没有被推翻，只是没被这道题触发**。检索机制确实弱，
只是知识库小到让检索这一环不必存在。

**对文章的三条直接含义：**

1. **第 01 篇不能拿这道题当「它检索能力强」的证据。**能写的是：知识库小的时候，它会全量读，
   所以准；这个准是**规模给的，不是能力给的**。
2. **清单第一节说这道题「大概率会暴露平台检索边界」，这个设计目标本次没有达成。**
   要暴露那条边界，得把知识库做到全量装载不可行的规模——那是第 11 篇的事，不是第 01 篇的。
3. **「知识库里放什么决定它答得准不准」这句话要补一个变量：还取决于放了多少。**
   同样三份文件，扩到三百份，这道题的表现可能完全不同，而学员不会预期到这个拐点。

### 三之二 · 「传完立刻提问」这条常见错误不成立

清单步骤 2 写着「索引更新有几秒延迟，而界面可能不给任何提示」，列为常见错误。
🟢 **实测不成立。**

探针做法：写入第四份文件，内含三份正式文件里都没有的事实（补单时限 36 小时、
内部代号 ZX-7731），**上传返回后 3.55 秒**即提问，中间不等待。回答两个新事实全部命中。

原因就是三之一那条：**这个平台在 Bot 这一侧没有索引层**，它直接 `find` + `Read` 文件系统。
没有索引，自然没有索引延迟。

**清单那条要改。**改成什么要看界面那一遍——界面上传可能另有异步处理，本次只证明了
API 写入路径没有延迟。**在界面复核之前，正文里不要写「不用等」，也不要写「要等十几秒」，
两个都还没有依据。**

### 三之三 · 那次探针顺带撞出一件没设计的事：它自发做了冲突提示

系统提示词五条里**没有任何一条**要求它处理口径冲突。但它主动做了：指出临时文件与正式文件
就补单时限存在矛盾，评估了临时文件「没有版本号、生效日期和责任部门发布格式」，
给出以正式文件为准的建议，并要求向责任部门确认。

第 11 篇要求的「同一问题多个口径要提示冲突」，它在这个规模下自发满足了。

⚠️ **但这条不能写成平台能力或可依赖行为。**它是一次观察，是模型自发行为，提示词里没写。
它和第 17 篇那条「提示词管不住『不做什么』」是同一枚硬币的两面：
**提示词没写的「要做什么」，它也可能自发做——两个方向都不能依赖。**
要让冲突提示成为可依赖的行为，得写进提示词并且用评测集验，那是第 16 篇。

### 三之五 · 三条只影响写脚本的人（正文不必提，操作说明可留）

🟢 `GET /files/content` **返回裸文本，不带 `code`/`data` 包封**，与同仓库其他端点不同构。
按统一包封解析会当场炸——AGENTS.md 硬约束第 3 条「响应按端点解析」的又一个实例。

🟢 `GET /chat/conversations/{id}/messages` 的数据在 **`data.messages`**，不是 `data.list` 或 `data.items`；
`limit` 上限 **100**（传 200 报 400），不接受 `page`/`pageSize`/`order`。
解析键写错时接口返回 **HTTP 200 加空列表**，而会话列表同时报 `messageCount=6`——
**看起来完全像「平台把历史弄丢了」**。本次差一点就据此往事实层写进一条错误的平台事实，
先看裸响应才拦住。同源于事实清单第八节第 6、10 条那两次教训。

🟢 **同一次回答内，`createdAt` 与 `blockIndex` 的顺序是相反的**：正文块 `blockIndex=4` 的
`createdAt` 早于 `blockIndex=0` 的工具块。手册只记了「按 createdAt 倒序返回，必须显式正排」，
**正排也不对**——块内必须按 `blockIndex` 排，否则拼出来的答案顺序是乱的。

## 五、交付给第 02 篇的证据

清单第六节要的三条，全部拿到，其中第三条比预想的更有力。

| 第 02 篇要论证的 | 🟢 本次证据 |
|---|---|
| **只读**——没有写入任何系统 | 全程未配置任何工具与权限。五题的工具轨迹只有 `Bash`（`find`/`grep`）与 `Read`，**零写操作** |
| **只生成**——产出只有文字 | 五题回答形态全部是文本，无任何副作用 |
| **结果可自检**——答案能回去对原文 | 见下 |

**第三条的证据形态比清单预想的强。** 清单原本担心的是「模型写的出处会编造」，
所以口径定成「它给的出处，你能回去对。可自检的主语是你，不是它」。这个口径**不用改**，
但第 4 题给了它一个更硬的支撑：

```text
[1] Bash   grep -n "回滚" /workspace/*.md
           → 提单与验收流程.md:63:- 高风险变更缺回滚方案
             研发变更管理办法.md:32:| 高风险 | 架构负责人，且业务负责人会签 | 影响范围说明、**回滚方案**、验证方案 |
             研发变更管理办法.md:47:- 高风险变更未附回滚方案
```

三处命中**全部是把回滚方案当作审批材料**，没有一处规定「执行回滚由谁批」。
于是它回答「流程文件里没有直接写到这一条」——**这个结论有 `file:line` 级的证据可核**，
而且核的方式就是学员自己去 `grep` 一遍，或者在界面上翻那三份文件。

**第 4 题落在了好的那一支。**它承认了知识缺失，没有编。所以第 02 篇「结果可自检」
这个论断立得住，第 15 篇与第 20 篇拿不到本次的反面教材——那两篇要另找样本，
或者用第 2 题里那句它自己标出来的不确定（「文件里未写明这里的『退回』是否包含验收环节退回，
建议向研发管理办公室确认口径」）。

**一条给第 16 篇的意外收获。** 第 5 题它指出：「处理中」这一步**流程文件里没有写时限**，
所以算不出从提单到上线的总时长。这是**我们自己写这三份文件时没意识到的缺口**——
知识库的洞是被 Agent 问出来的，不是被人审出来的。第 16 篇讲评测集时，这是一个现成的例子：
**评测集的价值不只是判 Agent，也在判知识库。**

## 七、界面复核（2026-09 站主亲验，补记）

前六节是 REST API 那一遍的产物，纯界面问题原样留着。本节是站主登录后补的，**只记亲眼看到的**。

### 七之一 · 平台渲染的是「轨迹」，不是「出处」

回答正文上方是一组平台组件，每行带绿点与对勾、右侧 `>` 可展开：

```
>_ Bash  ✓  List markdown files in workspa…
📄 Read  ✓  提单与验收流程.md
📄 Read  ✓  变更风险分级表.md
📄 Read  ✓  研发变更管理办法.md
```

而正文里的「依据：《提单与验收流程》第四条…」是**斜体引用块**，模型自己写的 markdown。

| | 谁产生 | 可信 | 粒度 |
|---|---|---|---|
| 轨迹 | 平台，来自工具执行 | 🟢 可信，它伪造不了自己调了什么 | 到文件 |
| 出处 | 模型，写在正文 | ❌ 会编，有实测前科 | 到条款 |

三条界面细节（🟢 亲验）：**展开 `>` 里只有文件路径、没有内容**；
**文件名可点、点了打开对应文件**；**官方文档说的三个操作按钮界面上一个都找不到**，悬停也没有。

**由此定出第 02 篇的「可自检」链，三步全要人做**：
看轨迹知道它读了哪几份 → 点文件名打开原文 → 拿模型写的「第四条」回去对。

### 七之二 · 那张轨迹图直接坐实了三之一

界面上那三行 `Read` 把三份文件逐一列了出来——**API 工具轨迹里看到的「它全读了」，
界面原样画了出来**。「知识库小的时候它不检索、直接全量读」这句话因此不必解释，
读者一眼就看见。**这是第 01 篇最重要的一张插图。**

  **这枚芯片是判断「走在哪条路上」的唯一可视凭据。**
