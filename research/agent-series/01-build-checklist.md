## 零、拍第一张图之前必须先定的三件事

这一节不是准备工作，是**不可逆决策**。三样东西一旦进了第一张截图就锁死了，
后面二十二篇全部得跟着走。

### 零之一 · 演示身份：脱敏必须从源头解决

计划书第五节的原话是「别指望每张图手工涂抹」。二十三篇两三百张图，
手工涂抹这条路走不通，所以身份问题必须在建空间那一刻就解决掉。

| 会出现在截图里的 | 可控吗 | 怎么办 |
|---|---|---|
| 工作空间名 | 可控 | 建空间时直接用中性名，见下表 |
| Bot 名 | 可控 | 同上 |
| 知识库文件名 | 可控 | 用本清单配套的三份演示文件 |
| **组织名** | 不可控 | 出现在空间切换器与面包屑里，**靠取景避开** |
| **账号头像与显示名** | 不可控 | 出现在右上角，**靠取景避开** |

**取景避开这条不是将就，它是免费搭车的。** 下一节会推出「单张截图取景宽度上限约
670px」这个硬约束——为了字看得清，本来就不该截整个浏览器窗口。而顶栏、侧栏、
右上角头像天然落在 670px 的取景框之外。**清晰度约束和脱敏约束指向同一个动作。**

例外是少数必须拍到导航位置的图（比如「空间设置」入口在哪）。那几张单独处理：
要么当场涂掉那一小块，要么改用箭头标注的局部图。数量控制在两张以内。

**现在定死，之后不要改：**

| | 取值 | 理由 |
|---|---|---|
| 工作空间名 | `研发流程问答（演示）` | 带「演示」二字，读者一眼知道这不是生产环境 |
| Bot 名 | `流程助手` | 中性、与场景一致、后面二十篇继续用 |
| 知识库目录 | 根目录直接放三份文件 | 01 篇不引入目录层级，第 11 篇再讲 |

### 零之二 · 取景宽度：操作截图的硬约束

这一条是从本站的正文容器宽度反推的，跟第 7 篇那次「19px 的字缩到 7px 变成一团墨」
是同一个病，只是这次更严重——**结构图的字号是我们能改的，平台界面的字号改不了。**

算一遍：

```
本站正文容器宽度        574 px（手册记录值，保守取小；CSS 推算为 640 px，待重量）
knodo 界面正文字号      约 14 px
希望它在博客上不小于    12 px
允许的缩放比            12 / 14 = 0.857
截图取景宽度上限        574 / 0.857 ≈ 670 px
```

**结论：一张操作截图，画面里横向装下的界面内容不得超过约 670 个 CSS 像素。**
那大概是一个对话框、一块设置面板、一段表单的宽度。

反面对照：整窗口截图按 1440px 算，缩到 574px 是 0.40 倍，14px 的界面字变成 5.6px。
那就是第 7 篇踩过的那团墨，而且没有补救余地。

**文件像素数要给到 1200~1400。** 两条路二选一：

- HiDPI 屏：浏览器缩放保持 100%，直接框选约 670px 宽的区域，得到约 1340 物理像素
- 普通屏：**把浏览器缩放调到 200%**，再框选约 1340 物理像素宽的区域（对应 670 CSS px 内容）

两条路等价。缩放调完不要中途改，否则前后几张图的界面大小对不上。

### 零之三 · 贯穿场景：研发变更流程

**2026-09 改的。**原设计是差旅申请（计划书第七节），改成研发变更流程，
理由不是省事，是**统一**：风险分级 L1–L4 那根主轴能在同一条流水线上把四级全举完。

| 等级 | 同一条流水线上的例子 |
|---|---|
| L2 受控问答 | 查流程制度答疑——**第 01 篇搭的就是它** |
| L3 受控执行 | 帮人提单、填要素、追踪到哪一步 |
| L4 高影响执行 | 自动改代码并发布到生产 |

原设计要拿三个不相干的场景各举一个（差旅撑 L2/L3、对账开票撑 L4、
开发流水线撑多 agent），读者每隔几篇重建一次场景。统一之后，
第 04 篇「把批准对象从结论换成清单」用发布场景讲也更自然——
批的是一份具体的发布清单，不是「可以发」这三个字。

第 01 篇只做这条流水线的**只读问答**那一段，提单与审批留到第 03、04 篇。

这个场景一旦在第 01 篇露面，往后一路都跟着它：

| 篇 | 怎么复用 |
|---|---|
| 02 | 拿 01 的产物当解剖对象，论证它为什么是低风险 |
| 03 | 同一条流水线上定出 L2 / L3 / L4 三个档 |
| 04 | L4 解剖对象换成「自动发布到生产」，与本场景同源 |
| 05 | 二十个字段的登记表就填这个项目 |
| 06–10 | 九个控制项的贯穿例子 |
| 11 | 知识库的来源、版本、有效期，用的还是这三份文件 |
| 15 / 20 | 异常路径与退出机制，接第一节第 4 题那个回滚缺口 |
| 16 | 评测集的种子就是本清单第一节那五道验收题 |
| 21–23 | 多 Agent 那三篇本来就用开发流水线，底稿是 `somp-flows-analysis.md` |

**注意 21–23 篇不需要再搭一遍。**那三篇是解剖一条已经在跑的流水线，
样例先行的要求（计划书第五节）只约束 01–05，而那边的「样例」是通读产出的分析底稿。

所以配套的三份演示知识文件要**版本固定、入库**，见 `01-demo-kb/`。

## 一、演示知识库与五道验收题

### 三份文件

放在 `research/agent-series/01-demo-kb/`，直接上传，不要改内容。

    研发变更管理办法.md  变更分类、审批原则与权限、变更窗口、不予受理情形
    提单与验收流程.md    提单要素、状态流转、各节点时限、验收规则、退回原因
    变更风险分级表.md    高/中/低三级各自的判定条目

**这三份是为演示写的虚构制度，不对应任何真实公司或真实系统。**
形态照 SOMP 的 `docs/bizdocs/` 抄（步骤编号、门禁、超时与升级、状态流转），
内容全部虚构——**保留形态、换掉内容**，脱敏才能从源头解决。真文档传上去再截图，
等于公开发表内部资料，而那个目录里还躺着带公司标识的文件。

**它们的结构是刻意设计的**：《管理办法》第三条只说高风险变更要谁批、要附什么材料，
**不说哪些变更算高风险**——那写在《变更风险分级表》里。于是「改支付回调的接口谁批」
必须先查分级表（资金链路 = 高风险），再回管理办法（架构负责人批 + 业务负责人会签
+ 须附回滚方案），两跳。这是故意的——`knodo-platform-facts.md` 第五节记着平台的检索
「只有关键词/文件级，没有平台级向量或统一检索」，这道题大概率会暴露那条边界。

计划书第五节说「卡在哪儿就是那一篇该写的内容」。这道题卡住的地方，就是第 01 篇
「常见错误」那一段的正文，也是第 11 篇的引子。

### 五道验收题

按顺序问，**每一问的原话和它的原答都要抄进 `01-build-log.md`**。

| # | 问题 | 预期 | 测的是什么 |
|---|---|---|---|
| 1 | 提单之后多久会有人处理 | 答得出（受理 1 个工作日） | 单文件直答，基线 |
| 2 | 验收不通过会怎么样 | 答得出（退回写明不符之处，时限重算，连续 3 次升级） | 单文件直答，换一份文件 |
| 3 | 我要改支付回调的接口，谁批 | ~~大概率答不好~~ → 🟢 **实测答得完全正确**，但原因不是它检索强，是知识库太小（见下） | 原设计是跨文件两跳，**本次没测到** |
| 4 | 上线之后要回滚，回滚需要谁批 | 应该说「流程里没写」 | 知识缺失时它是承认还是编 |
| 5 | 我提的这个需求什么时候能上线 | 应该反问风险等级或变更类型 | 分档条件下会不会先问再答 |

### ⚠️ 第 3 题的设计 2026-09 实操失败了，而失败比成功有价值

🟢 工具轨迹显示它 `find` 之后把**三份文件整篇读进了上下文**（合计 2.6 KB）。
所谓「两跳」在它眼里不是两跳——两条依据都在同一份上下文里，**它根本没走检索**。

所以「平台检索只有关键词/文件级」那条论断没被推翻，只是**没被这道题触发**：
检索机制确实弱，只是知识库小到让检索这一环不必存在。

**换来的三条比原设计更值钱：**

1. 第 01 篇不能拿这题当「它检索强」的证据。能写的是：知识库小的时候它会全量读，所以准，
   **这个准是规模给的，不是能力给的**。
2. 要暴露检索边界，得把知识库做到全量装载不可行的规模——**那是第 11 篇的事**。
3. 计划书给第 01 篇写的那句坑「知识库里放什么决定它答得准不准」，
   **要补一个变量：还取决于放了多少**。学员在十份文件上验收通过，上线时是三百份，
   **而他不会预期到这个拐点。**

### 第 4 题仍然是最关键的一道

这个缺口是**真实流程里也会有的那一种**——三份文件都写了
「高风险变更须附回滚方案」，却没有一份写「执行回滚由谁批」。
**它承认不知道，第 02 篇「结果可自检」那个论断才立得住；它编一个出来，
第 15 篇「知识缺失必须停下来」与第 20 篇「退出机制」就有了现成的反面教材。**
两种结果都能用，但必须如实记录。

## 二、四步搭建 · 逐步取证

每步四段，跟第 01 篇的正文结构一一对应：**做什么 → 怎么做 → 应看到什么 → 常见错误**。

**「怎么做」在这里只给一句话，具体点法在 `01-knodo-operations.md`。**
两份文档职责分开：这份是方法层（为什么这么搭、要看到什么、别踩什么、截哪张图），
那份是平台层（点哪儿、填什么）。同一件事不写两遍，否则必然漂移。

> **2026-09 由五步改成四步。**原设计第 3 步是「写工作指引」，取消了。
> 官方文档 FAQ（`llms-full.md:8180-8184`）写明：**通过助手聊天用的是助手的系统提示词，
> 在空间内直接聊天用的才是工作指引，二者不叠加。**本篇搭的是 Bot，
> 工作指引里写的规矩一个字都不会生效。这条没被文档挡下的话，
> 跑出来会是一个「看着都配好了、实际有一半没接上」的 agent，而界面上看不出来。
> **它现在是步骤 3 的头号常见错误。**

### 步骤 1 · 建工作空间

**做什么。** 开一块隔离的地方，这个 agent 的知识、对话、成员都圈在里面。

**怎么做。** 新建工作空间，名字填 `研发流程问答（演示）`，可见性选**私有**，其余默认。
→ 操作说明第一节。

**应看到什么。** 左侧出现这个空间，进去之后有知识、对话等入口。

**常见错误。**

- **一上来就去组织设置里配 API Key。** 那个 Key 只是大模型渠道，回答的是
  「用谁的模型算」，碰不到空间数据。搭这个 agent 一次都用不到它。
  平台事实清单把「拿它当平台 API 凭证」列为最常见的错误，第 01 篇要一句话挡掉。
- **顺手选了模板。** 平台提供空白 / 团队协作 / 项目管理 / 知识管理四个模板，
  后三个会预置知识结构与指引。第 01 篇要的是空白起点，读者得看清每样东西是怎么来的。
- **以为要先选模型。** 模型不在建空间的表单里，新建空间默认用 Claude Code，本篇不动它。

**截图。** 图 1 —— 新建空间的表单，名字已填、尚未提交。取景只框表单本身。

### 步骤 2 · 上传知识库文件

**做什么。** 把三份流程文件放进这个空间的知识库。

**怎么做。** 进左侧「知识」，用工具栏的「上传」传 `01-demo-kb/` 里的三份 `.md`，
放根目录，不建子目录。→ 操作说明第二节。

**应看到什么。** 文件树里三份文件齐全，点开能看到渲染后的内容。

**常见错误。**

- **以为知识库是个数据库，传上去就会被「学习」。** 它本质是一个基于 Git 的文件仓库，
  agent 用的时候是去里面**找**，不是提前记住。这个区别决定了下一条。
- **文件名起得随意。** `制度1.md` 和 `提单与验收流程.md` 的命中率不是一回事——
  检索机制未确认，但文件名很可能就是检索线索。
- ~~**传完立刻提问。**~~ 🟢 **2026-09 实测撤销**——API 路径 3.55 秒即命中，Bot 侧没有索引层。
  界面路径待复核，在那之前「要等」和「不用等」两句都不能写。
  **划掉不删**：一条听起来极合理的「常见错误」被实测推翻，这本身就是第 01 篇能用的素材。

**截图。** 图 2 —— 知识库文件树。取景只框文件树区域。
⚠️ 🟢 **根目录实际四个条目**，平台自建了一个 `.gitignore`，说明文字要提一句，
否则读者以为自己传错了。

### 步骤 3 · 新建 AI 成员（Bot）

**做什么。** 造一个有名字、有职责的 AI 成员——**这一步才是让读者「看见 agent 长什么样」的那一步**。

**怎么做。** 进空间 → 左下角「设置」→「AI 成员」标签 →「新建 AI 成员」，
名称填 `流程助手`，**规矩全部写进系统提示词**（原文见操作说明第三节），可见性保持私有。
→ 操作说明第三节。

**应看到什么。** 空间的 AI 成员列表里出现 `流程助手`，可以对它发起对话。

**常见错误。**

- **把规矩写进工作指引。** 头号错误，见本节开头那段改动说明。新手一定会先看见左侧那个
  「工作指引」菜单、把规矩认真写进去，然后建 Bot、开始对话——那段规矩一个字都不生效，
  而界面上看不出任何异常。**这是第 01 篇最值钱的一条，因为它是静默的。**
- **把三份流程文件的正文粘进系统提示词。** 后果有三样：固定占掉上下文、
  **答案里没有出处**（它不是查到的，是被直接告知的）、改一次制度要回来改提示词。
  分工是：**系统提示词说「它是谁、按什么规矩办事」，知识库说「事实是什么」。**
- **规矩写成愿望。** 「请尽量准确」「不要出错」管不住任何东西。写进去的五条每一条
  都对应一个可观察的动作，这才是能验的。
- **建完不管可见性。** 默认 `PRIVATE`，仅创建者可见。演示空间保持私有就行，
  但读者会以为建完同事就能用了，正文要点破。
- **顺手去点「个人技能」Tab。** 那是绑 Plugin 的，属于打包与注册那一段，第 12 篇才讲。

**截图。** 图 3 —— 新建 AI 成员的表单，名称与系统提示词已填。取景只框表单。

### 步骤 4 · 对话验收

**做什么。** 按第一节那五道题依次问，把原答抄下来。

**怎么做。** 新开一个对话，**先确认输入框工具栏显示的是 `流程助手`**（助手选择只在新对话
开始前生效，没选中就走了另一条路），然后一题一题问，不要在同一轮里连问两题，也不要用 `@`
手动引用文件——要测的正是它自动检索的能力。→ 操作说明第四节。

**应看到什么。** 第 1、2 题答得出；第 3 题的表现是本次搭建最值钱的观察；
第 4 题看它承认还是编；第 5 题看它反问还是直给。

**常见错误。**

- **没确认助手名就开始问。** 没选中 Bot 时，走的是工作指引那条路，测的不是你搭的东西。
- **拿一道自己也不知道答案的题去验。** 验收题必须是你能当场对着文件核对的，
  否则你验的不是它，是你的印象。（第 16 篇展开。）
- **只问顺利的那两题就收工。** 那样得到的是一个「看起来能用」的 agent，
  而这个系列全部的价值在于知道它**哪儿不行**。

## 四、截图规格与落盘

| 项 | 规定 |
|---|---|
| 取景宽度 | 界面内容 ≤ 670 CSS px（见零之二） |
| 文件宽度 | 1200~1400 物理像素 |
| 格式 | PNG。界面截图是大面积纯色加细小文字，JPEG 会在文字边缘起振铃 |
| 单张体积 | ≤ 120 KB（一篇七张约 800 KB） |
| 落盘 | `app/public/images/` |
| 命名 | `agent-01-<序号>-<英文短名>.png`，如 `agent-01-5-first-answer.png` |
| 正文引用 | `/images/agent-01-5-first-answer.png`——**根路径**。写相对路径在 HashRouter 深链下会指错目录 |
| 标注 | 箭头与框，只标一处重点。计划书说操作截图「不需要设计，只要清晰」 |

压缩（本机没有 pngquant，用 Pillow 的调色板量化，界面截图压得很干净）：

```bash
python3 - <<'EOF'
from PIL import Image
import os, glob
for src in sorted(glob.glob('/tmp/shots/agent-01-*.png')):
    dst = 'app/public/images/' + os.path.basename(src)
    im = Image.open(src).convert('RGB')
    if im.width > 1400:
        im = im.resize((1400, round(im.height * 1400 / im.width)), Image.LANCZOS)
    im.quantize(colors=256, method=Image.MEDIANCUT).save(dst, optimize=True)
    print(f'{os.path.basename(dst):40s} {im.size}  {os.path.getsize(dst)//1024} KB')
EOF
```

超过 120KB 就把 `colors` 降到 192 或 128 再看一眼字有没有糊。

**公众号侧不用另做。** `scripts/wechat/api.mjs` 认 `.png`（走 `image/png`），
正文图片会自动传素材库并按内容 hash 去重。但计划书第五节那条要记着：
**永久素材有数量上限，二十三篇的账要提前算。**

## 六、这一遍顺带交付给第 02 篇的东西

不用额外做事，跑的时候心里有数即可。第 02 篇要论证 01 的产物是低风险，
靠的是三条特征，而这三条的证据全在这次搭建里：

| 第 02 篇要论证的 | 证据来自 |
|---|---|
| 只读——它没有写入任何系统 | 全程没配任何工具与权限，四步里一处都没有 |
| 只生成——产出只有文字 | 五道题的回答形态 |
| **结果可自检——答案能回去对原文** | 见下，2026-09 已定案，但**口径要改** |

**第三条 2026-09 定案了，而且它改了第 02 篇的写法。**

🟢 解析原始取证 JSON：会话消息的 **35 个**字段里**没有任何出处类字段**（唯一形似的
`imSource` 是 IM 渠道来源）。2026-09 实操复核，原记 33 个已订正。
所以官方那句「AI 回答会注明信息来源」不是平台能力，是**模型自己在正文里写**——
平台把这件事交给了 Bot 的系统提示词（自带模板里就写着「引用原文」）。

而模型写的出处**会编造**。🟢 实测前科：某次报告称「首轮报告已记录此复制」，
而首轮四条发现无一涉及此事；工具轨迹显示它读过原文，属于「看了却说反」。

**所以第 02 篇不能写「它会给出处所以可信」，要写：**

> **它给的出处，你能回去对。可自检的主语是你，不是它。**

这个口径跟全系列主轴是同一句话——判据只有一种，自己回去看。
唯一还要登录确认的是**界面上有没有额外渲染**（数据结构里没有，不等于前端不解析正文），
在操作说明第六节第 1 项。
