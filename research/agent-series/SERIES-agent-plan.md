# AI Agent 实战系列 · 内容规划 v0.1

> 状态：待站主审阅。发布前逐篇过脱敏检查。
> 载体：公开博客新轨，标题带序号（《AI Agent 实战 03 · …》），零前端改动。
> **方法平台无关**；knodo 只作演示载体，换 fastgpt 等平台方法同样成立。

---

## 一、这个系列教什么

**不是教怎么写提示词，是教怎么把一件业务上的活，安全地交出去一部分。**

学员学完能主导一个 agent 项目：知道要干哪些活、哪些能交给 AI、哪些是自己作为
产品经理必须拍板的、以及做出来之后怎么判断它行不行。

**不教的**：模型原理、编程、平台运维。需要写代码的地方明确说「这里要找工程搭档」，
并教到「能跟工程师对话」为止。

## 二、读者与前提

业务专家，梳理需求是强项，**没有开发经验，没搭过 agent**。
手上有真实需求想自己动手。

因此全系列两条纪律：术语先讲动作再报名字；每个抽象判断后面必须跟一个
他们业务里真实发生过的场景。

## 三、主轴：风险分级

贯穿全系列的那根轴不是技术难度，是**风险等级**。
一个 agent 能自动到什么程度，不看它多聪明，看它碰什么。

| 等级 | 它在干什么 | 能自动到什么程度 |
|---|---|---|
| L1 辅助生成 | 写草稿、做总结、解释东西 | 人看过再用 |
| L2 受控问答 | 查制度、查资料、答疑 | 来源可追溯，按权限检索 |
| L3 受控执行 | 建任务、填单据、发起流程、调内部接口 | 白名单 + 最小权限 + 关键动作人工批 |
| L4 高影响执行 | 碰钱、碰客户承诺、碰合规判断、碰生产 | 原则上不允许无人值守 |

依据 ISO/IEC 42001 的管理思路整理。**这张表是全系列引用最多的一张。**

## 四、写作规范（与现有博客不同轨，动笔前先读）

现有七篇是专栏，靠钩子拉着读者线性往下走。**这个系列是操作手册，读者是查阅式使用的**——
搭到一半卡住，回来扫目录找那一篇。两种材料的使用方式相反，写法必须跟着换。

**标题是索引，不是钩子。**说清这一篇讲什么、能得到什么，结论放进标题里，不藏。
不用设问句、不用悬念、不拟人化。判据：学员两周后回来查资料，看标题能不能想起里面讲了什么。

**段落节奏是「这一步做什么 → 怎么做 → 做完应该看到什么 → 常见错误」**，
不是「设问 → 短答案 → 展开」。后者是专栏的引擎，用在操作手册上会让读者找不到重点。

**术语直接用，第一次出现给一句定义就够。**读者是业务专家不是零基础大众，
不需要生活化比喻做台阶。比喻可以有，但只能用来解释，不能承重。

**表格优先于散文。**分级、清单、矩阵、字段说明，一律用表格。合规文档本身就是表格为主，
照抄形态。表格在博客与公众号都原生渲染，读者还能直接复制去用。

**平台无关的方法与平台具体操作必须分层写，并显式标注。**
每篇先讲方法——换个 Agent 平台照样成立的那部分；再给 knodo 上的具体点法作为一次实例。
不分层的话，换平台整篇作废，读者也分不清哪些是原理、哪些是这个平台的特性。

**每篇必须有产出物。**学完手上要多一个东西：一份填好的表、一个跑起来的 Agent、
一套评测集。没有产出物的篇目说明还没想清楚它存在的理由。

## 五、样例先行（必须在写文章之前）

**先按教学路径真搭一遍，再写文章。**不是为了配图，配图只是副产品。

理由是现成的：knodo 摸索项目里最值钱的那些结论——「已发布／已绑定／组件非空」三者
每一层都替代不了下一层、超时的更新请求其实持锁挂起导致后续三小时全被拒、
组件列表在重传期间会瞬时归零——**没有一条是读文档能读出来的**。
不真搭一遍，写出来的会是「应该是这样」，而不是「实际是这样」，
而这个系列的全部价值在后者。

做法：建一个中性命名的演示空间，按 01–05 的顺序真搭一个研发流程 Agent，
边搭边记。**搭到第几步对应第几篇，卡在哪儿就是那一篇该写的内容。**

### 图分三类，做法完全不同

| 类型 | 占比 | 做法 |
|---|---|---|
| 操作截图 | 绝大多数 | 真实界面，加箭头与框。不需要设计，只要清晰 |
| 结构图 | 少量 | 流程、层级、边界。**字号按正文容器宽度反推**——本站容器桌面端 574px，画布上排的字缩完会看不清；正文插图第一标准是看懂，不是好看 |
| 表格 | 很多 | **不要做成图片。**分级表、登记模板、权限矩阵一律用 markdown 表格 |

把第三类摘出去之后，真正要做的图少一半，剩下的都是非做不可的。

### 三个工程约束

**公众号素材配额。**正文图片要传微信永久素材库，而永久素材有数量上限。
一篇十几张截图、二十二篇就是两三百张。按内容 hash 去重只对重复图有效。
量要提前算，或接受某几篇公众号版不带图。

**页面重量。**十几张截图一篇，加载与流量都要考虑，截图必须压缩。

**截图脱敏。**平台界面会带空间名、组织名、用户名、头像。
**从源头解决**——专门建一个中性命名的演示空间，别指望每张图手工涂抹。

## 六、二十三篇

### 第一部分 · 先看见它（2 篇）

**01 · 创建第一个问答 Agent（全程无代码）**
全程点击，不写一行代码。建空间、传几份资料、写一段 System Prompt、跟它对话。
先让他们看见 agent 长什么样——没搭过的人，讲再多概念都是空的。
> 产出：一个真在跑的问答 agent
> 坑：知识库里**放什么、以及放了多少**决定它答得准不准，第 11 篇细讲。
> **「多少」这个变量是 2026-09 实操加的**：知识库小到能全量读进上下文时，
> 它根本不走检索，所以答得准——**那个准是规模给的不是能力给的**，
> 而学员在十份文件上验收通过、上线时是三百份，不会预期到这个拐点

**02 · Agent 的风险来源与分级依据**
以第 01 篇的产物为对象，说明它属于只读、只生成、结果可自检三种低风险特征，
因而无需额外控制。再列出四类使风险升高的因素：写入系统、影响外部方、
结果不可自检、动作不可逆。
> 产出：能说明「能否直接上线」由风险特征决定，而非技术难度
> 覆盖：低风险特征、四类风险升高因素
> **模型是第五个风险因子（2026-09-06 实操新增）**：knodo 上 Bot 与模型解耦——
> Bot 定「它是谁、按什么规矩办事」，模型定「用什么算」，而模型是**对话级可换的**。
> 实测同一道题、同一知识库、同一段提示词，qwen3.8-flash 三处引用两处有问题，
> glm-5.2 全对且多标出三个知识库空洞。**两版读起来同样自信规范，
> 你无法从答案本身判断可靠性。**这条比原设想的「出处会编」有力——
> 「会编」听着像能靠经验规避，这个不是。第 03 篇定级时它是**分级表里没有的那一格**

### 第二部分 · 定级与立项（3 篇）

**03 · 风险分级 L1–L4：判定方法与依据**
L1 到 L4 怎么判，判据是什么。**三个对照场景取自同一条流水线**（2026-09 改，见第七节）：
查流程制度答疑（L2）、帮人提单并追踪进度（L3）、自动修复并发布到生产（L4）。
同场景对照的好处是变量只剩一个——**它碰什么**——技术难度、领域、人员全都不变，
读者看得见分级到底由什么决定。
> 产出：给自己手上的需求定级，并写出定级依据
> 关键：定级不是走过场，它决定后面所有控制强度

**04 · L4 场景改造：把批准对象从结论换成清单**
解剖 L4 场景：自动修复一个支付回调的缺陷，并发布到生产。
按标准它同时命中资金链路、写入生产系统、动作不可逆、自动执行四条。
**但出路不是砍掉自动化，是把「人批准的对象」从结论换成清单。**
> 产出：把一个过不了门禁的方案改造成能过的
> 覆盖：定级复核、审批对象设计、执行一致性约束
> **2026-09 改**：原解剖对象是「对账后自动开票」。换成同一条流水线上的发布场景，
> 是为了跟 03 篇共用变量——三个对照场景只剩「它碰什么」一个变量在动。
> 「碰钱」这一维靠支付回调保住，没有丢。额外好处是它跟第 09 篇（审批粒度）
> 与第 21–23 篇（发布队列与批次）直接连上。**这一处是判断，不是你点的头，可回滚。**

**05 · 项目输入登记表：二十个字段逐项填写**
二十个字段的输入登记模板：业务目标、系统边界、风险等级、责任分工、
数据清单、工具权限、人工控制、测试要求、运行监控、退出机制。
逐字段讲怎么填，哪些自己能填、哪些必须去找 Owner。
> 产出：一份填好的登记表——这是项目本来就要交的东西，不是练习作业

### 第三部分 · Agent 合同（5 篇）

这五篇讲的是搭**任何**一个 agent 都要过的九个控制项。
差异只在工作内容、技能、输入输出；这九项对每个 agent 都一样。

**06 · 角色、目标与非目标清单**
一句话说清它替谁干什么活。重点在**非目标清单**——写不出「它不干什么」，
说明职责还没想清楚。
> 产出：角色卡的上半张

**07 · 动作分层与禁止动作清单**
把动作拆成读取 / 生成 / 建议 / 提交草稿 / 触发流程 / 写入系统 / 对外发送七层。
层级越往后风险越高。禁止清单要显式写，例如不得绕过审批、不得直接承诺客户。
> 产出：动作权限矩阵
> 关键：这一层没拆清楚，后面的审批点就没法放

**08 · 工具白名单与最小权限配置**
默认只读；要写权限必须按场景、对象、字段、操作拆开授权。
工具不止平台内置的那些，也包括对外部系统的调用——接口从哪来见第 13 篇。
「让它自由选择工具」是明确不允许的实现方式。
> 产出：工具清单 + 权限矩阵

**09 · 人工审批点：位置、粒度与一致性**
接第 04 篇。**批准的必须是一份具体可执行的清单，不是汇总结论；
批准之后执行的必须严格等于那份清单，不能重新生成。**
还要定粒度：一次确认授权五百次写入，那这一次点击就扛了五百次的责任。
> 产出：审批点设计 + 粒度规则
> 覆盖：批准对象的粒度、批准与执行的一致性校验

**10 · 可追溯日志与版本管理**
要记的字段：用户、输入、引用来源、模型版本、提示词版本、工具调用、输出、
审批人、执行结果。
> **两个平台侧的真缺口（2026-09 实操）**：会话消息 35 个字段里**没有任何出处类字段**，
> 出处是模型写在正文里的；`modelId` 字段**存在但实测全部为 `null`**。
> 也就是说「引用来源」与「模型版本」这两项，**平台目前一项都不满足**。提示词、工具、知识库、模型、评测集变更都要留版本。
> 产出：日志字段设计
> 判据：出了问题能不能还原「它当时为什么这么做」

### 第四部分 · 在平台上落地（4 篇）

**11 · 知识库：来源、版本、有效期与废止机制**
知识库不是文件堆。每份知识要有来源、版本、更新时间、失效时间、责任人。
同一问题多个口径要提示冲突；引用过期文档要显式标记。
> 产出：知识库目录
> 坑：把领域知识塞进全局指令，会固定占用上下文且丢失出处
> **规模拐点（2026-09 实操新增，本篇独有）**：小知识库它全量读、不检索，所以准；
> 大到读不动才开始走检索，而这个平台的检索只有关键词/文件级。
> **第 01 篇那个「答得准」的体验会在这里失效**，本篇要负责把拐点讲明白并给出判断方法。
> 另：「同一问题多个口径要提示冲突」实测它在小规模下**自发做到了**（提示词里没写）——
> 但一次观察、模型自发，**不可当作可依赖行为**，要变成可依赖得写进提示词并用评测集验（第 16 篇）

**12 · 无代码的边界：哪些环节必须写代码**
划清无代码能走到哪：建空间、传知识、写 System Prompt、建任务、配定时、
设审查泳道——全都点得出来。**卡点在打包、注册、验证这三处。**
教到「能跟工程师说清楚要什么」为止。
> 产出：判断自己的需求要不要找搭档

**13 · 外部系统接入：接口盘点、缺口识别与源系统协作**
Agent 要干活就得调别的系统，而源系统未必已经提供了可调用的 API 或 MCP。
三个动作：盘点现有能调什么（API / MCP / RPA / 定期导出文件）；识别缺口——
拿不到是权限问题还是压根没接口；协作——写接口需求说明、谈权限范围（只读还是可写、
限定哪些对象与字段）、约定 SLA 与故障责任人。
还要讲清接口做不出来时的退路：人工导出上传、RPA 抓屏各自的代价与适用边界。
> 产出：接口需求清单、权限申请材料、退路方案
> 覆盖：对应合规输入包的「工具权限」与 A.10 第三方关系（接口方责任与 SLA）
> 说明：这块工作量常超过搭 Agent 本身，且属于业务顾问的强项——
> 跨部门协调、把需求讲清楚、争排期

**14 · 门禁的执行位置：必须在 Agent 之外**
沙箱里的 agent 手上有 shell，能跑脚本——也因此能绕过你给它划的边界。
**它自己跑门禁再报告「过了」，跟直接说「我做完了」没有区别。**
门禁必须在 agent 之外执行，结果写回来。
> 产出：理解「哪些交给 AI、哪些必须确定性」这条线画在系统边界上
> 覆盖：执行位置、结果回写、越权绕过的实测形态

**15 · 异常路径：五种必须停下来的情况**
模型不确定、知识缺失、权限不足、工具失败、结果冲突——五种情况都必须停下来找人，
而不是猜一个继续往下走。
> 产出：异常路径清单 + 对应的测试用例

### 第五部分 · 测试与上线（3 篇）

**16 · 评测集设计：标准问答、负例与回归**
几个正向样例不算测试。要有标准问答集、要有负例、要有回归——
知识库更新之后，原来答对的问题不能变答错。
> 产出：一套评测集

**17 · 红队测试：四类攻击面**
四类：提示注入、越权访问、错误工具调用、敏感信息泄露。
**提示词管不住「不做什么」**——这一条要用实测案例讲透。
> 产出：红队测试报告

**18 · 上线证据包：十四项清单与五道门禁**
十四项证据清单。核心原则一句话：**没有证据就不算完成，演示可用不等于可上线。**
> 产出：完整证据包
> 配套：G0 立项 / G1 设计 / G2 测试 / G3 上线 / G4 复盘 五道门禁怎么过

### 第六部分 · 运行（2 篇）

**19 · 运行监控：平台指标与自建指标**
平台原生给的：用量趋势、调用排名、使用热力图。
**平台不给的：答得对不对、有没有过期、有没有胡编。**那部分要自己造。
监控错误率、人工接管率、用户反馈。
> 产出：监控看板设计 + 告警规则

**20 · 退出机制：暂停条件、降级与回滚**
触发暂停的五种情况、降级方案、回滚预案。以及更常见的那种慢性退化：
知识过期、口径漂移、人工接管率悄悄升高。
> 产出：退出机制 + 复盘节奏

### 第七部分 · 多个 Agent（3 篇）

**21 · 流程拆分：职责边界与降级判定**
以一条开发流水线为例：理解需求并拆任务、写测试、写代码、跑测试、评审、发布。
每个 agent 一份合同，九个控制项逐个填。
> 覆盖：职责切分方法；降级判定——发布与测试执行属确定性设施，
> 仅「失败原因分析」适合由 Agent 承担

**22 · Agent 间交接：制品传递与门禁**
用任务系统传 handover。交接的是制品不是对话。
每一道交付物都要过门禁，而门禁在 agent 之外。

**23 · 确定性边界：不应交给 Agent 的工作**
收尾。**凡是「必须每次都一样」的事，一律不交给 agent。**
真实案例：自动拆解会过度拆分，一个小修复被拆成五个串行子任务，
五倍开销零收益。以及：不要信 agent 的自我报告，覆盖率要自己跑，
改动要自己从版本库提取。

## 七、先发哪五篇

二十三篇是大工程，但学员最急的只有两件事：**手上那个需求做不做得成、怎么开始。**
第 01 至 05 篇解决这两件事，发完他们就能自己判断该做什么、找谁。
其余十七篇慢慢补。

**练习场景 2026-09 由「差旅申请」改为「研发变更流程」**，理由是统一：
风险分级那根主轴能在同一条流水线上把四级全举完（L2 查流程答疑、L3 提单追踪、
L4 自动修复并发布生产），而第 21–23 篇本来就用开发流水线，读到那里时
读者已经在这条线上住了二十篇。原设计要拿三个不相干的场景各举一个，
读者每隔几篇重建一次场景。

练习仍统一落在「提单并追踪审批进度」上——L2 到 L3，学员自己扛得住，跑得通有成就感。
发布到生产那个留在第 04 篇当解剖对象，只拆不做。

两条配套约束：

**知识库内容必须虚构。**形态照 SOMP 的 `docs/bizdocs/` 抄，内容全部自造。
真文档传进演示空间再截图等于公开发表内部资料，而计划书第五节自己写过
「别指望每张图手工涂抹」。三份文件在 `01-demo-kb/`，版本固定。

**21–23 篇不需要再搭一遍。**那三篇是解剖一条已经在跑的流水线，
本节「样例先行」的要求只约束 01–05；那边的样例已经做完了，
就是 `somp-flows-analysis.md` 那一遍通读。
