### ② `app/src/lib/assets.ts`（新建）— 把 `blogs.ts` 里散的 base 前缀逻辑抽出来
系列封面和文章封面都要处理"本地相对路径 + 部署 base"这件事，写两遍就是重复，先抽出来：

```ts
/**
 * [INPUT]: 依赖 import.meta.env.BASE_URL（Vite 注入的部署路径前缀）
 * [OUTPUT]: 对外提供 resolveLocalAsset —— 本地相对路径补 base，绝对 URL/根路径原样放行
 * [POS]: lib/ 层的路径解析工具，被 data/blogs.ts（文章封面）与 data/series.ts（系列封面）共用。
 *        抽出此函数是为了不让同一段 base 前缀逻辑在两个数据文件里各自漂移
 * [PROTOCOL]: 变更时更新此头部，然后检查 CLAUDE.md
 */
export const resolveLocalAsset = (path: string): string =>
  !path || /^(https?:)?\/\//.test(path) || path.startsWith('/')
    ? path
    : `${import.meta.env.BASE_URL}${path}`;
```

### ③ `app/src/lib/markdown.ts`（改）— frontmatter 多解析一个字段
和 `category`/`tags` 平级，加在 `categoryMatch` 后面即可：

```ts
const seriesMatch = frontmatter.match(/series:\s*["']?([^"'\n]+)["']?/);
if (seriesMatch) metadata.series = seriesMatch[1].trim();
```
不给默认值——没有 `series` 就是没有系列，不能像 `category` 那样兜底成"未分类"，那会把所有零散文章误聚合进一个假系列。两个数据源共用这一份解析器（飞书文档也走它），所以飞书那边不用动。

### ④ `app/src/data/series.ts`（新建）— 系列封面的唯一登记表
系列封面不进文章 frontmatter：一个系列往往有好几篇文章，封面路径抄在每篇 frontmatter 里，改封面就要改好几处，这是典型的"数据泥团"。单独登记一次：

```ts
/**
 * [INPUT]: 依赖 @/lib/assets 的 resolveLocalAsset 补全部署路径前缀
 * [OUTPUT]: 对外提供 getSeriesCover —— 系列名到封面图 URL 的唯一映射入口
 * [POS]: data/ 层的系列元数据登记表，是系列封面的唯一权威来源。
 *        文章 frontmatter 只登记 series 名字，不重复填封面路径——
 *        避免同一系列的封面在多篇文章间各自抄写、进而互相漂移
 * [PROTOCOL]: 变更时更新此头部，然后检查 CLAUDE.md
 */
import { resolveLocalAsset } from '@/lib/assets';

// 系列名 → 封面相对路径（相对 public/，物理文件放 public/series-covers/ 下）
// 新增系列在此登记一行，无需改动任何页面组件
const SERIES_COVERS: Record<string, string> = {
  'AI 转型指南': 'series-covers/ai-transform.svg',
};

const DEFAULT_SERIES_COVER = 'series-covers/default.svg';

export function getSeriesCover(seriesName: string): string {
  return resolveLocalAsset(SERIES_COVERS[seriesName] ?? DEFAULT_SERIES_COVER);
}
```
物理图片放 `app/public/series-covers/`，跟现有 `covers/` 同级、同套路径解析逻辑，不用另发明规则。这两个 svg 文件（`ai-transform.svg`、`default.svg`）需要老杨手动放进去——我这边没有写文件的工具，给不了二进制。

在文件末尾加：
```ts
export interface SeriesGroup {
  series: string;
  cover: string;
  posts: BlogPost[];
}

/**
 * 按系列分组博客文章
 * 无 series 字段的文章不进入任何分组——分组视图只呈现成系列的内容，
 * 零散文章仍留在原有的时间线列表里，不强行归入"未分类系列"污染分组语义
 */
export async function getSeriesGroups(): Promise<SeriesGroup[]> {
  const posts = await getBlogPosts();
  const groups = new Map<string, BlogPost[]>();

  for (const post of posts) {
    if (!post.series) continue;
    const list = groups.get(post.series) ?? [];
    list.push(post);
    groups.set(post.series, list);
  }

  // posts 本身已按 date 降序，组内顺序随之保留；组间按各系列最新一篇排序
  return Array.from(groups.entries())
    .map(([series, seriesPosts]) => ({ series, cover: getSeriesCover(series), posts: seriesPosts }))
    .sort((a, b) => (b.posts[0]?.date ?? '').localeCompare(a.posts[0]?.date ?? ''));
}
```

## 2.品味自检

- **不引入系列本身的"数据源"**：`getSeriesGroups` 是对 `getBlogPosts()` 结果的纯前端聚合，不加缓存、不加新接口，飞书/静态两条链路零成本共享——符合"两相同构"，没有新增分叉逻辑。
- **封面路径解析只有一份**：`resolveLocalAsset` 抽出来之前，`blogs.ts` 里已经有一份 base 前缀逻辑，系列封面要是原地再抄一份，就是我在 CLAUDE.md 里读到的坏味道——"冗余：相同逻辑重复出现"。抽出去是唯一正确选择，不是过度设计。
- **系列封面登记表用纯 TS 对象、不是 markdown 文件**：这是刻意的。文章走 markdown 是因为"内容"天然该用 markdown 写；系列封面只是一张"名字→路径"的表，摆成 markdown 反而要多一层解析器，纯属为假想的灵活性加复杂度——踩了"过度设计"这条。写文章的频率远高于建系列，这一行代码的编辑成本可以忽略。
- **没有强行给零散文章分配"未分类系列"**：这个决定值得单独说一句——如果图省事把无 series 的文章都塞进一个虚拟分组，分组区就会显示一堆没有意义的卡片，用户分不清哪些是真系列。宁可分组区不显示它们，原有时间线列表继续原样兜底，语义干净。

## 3.改进建议（不在这次需求范围内，先不动手）

- 详情页（`BlogDetail.tsx`）加"本系列其他文章"导航条，读者读完一篇能顺着系列走，这是系列功能真正的价值所在，但当前需求只要列表页分组，先不越界。
- `series.ts` 里的封面表现在是纯手工登记，系列一旦超过一二十个会显得笨重，到那时候再考虑要不要挪成配置文件，现在没必要。
