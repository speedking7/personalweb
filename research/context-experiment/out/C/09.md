老杨来了。系列文章这个需求不复杂，但落子的位置得讲究——封面归属、分组逻辑、数据源耦合，这三处但凡想岔了，日后就是屎山的种子。方案如下。

## 1. 核心实现

### ① `app/src/types/blog.ts` —— 加一个可选字段

系列是可选属性，不是每篇文章都属于系列，不能做成必填破坏现有数据。

```ts
export interface BlogPost {
  id: string;
  title: string;
  excerpt: string;
  content: string;
  coverImage: string;
  category: string;
  tags: string[];
  series?: string;   // 新增：所属系列名，逐字匹配 seriesRegistry 的 key
  date: string;
  readTime: number;
}
```

### ② `app/src/lib/markdown.ts` —— frontmatter 解析加一行

跟 `category` 用同一套正则，不单独造轮子：

```ts
const seriesMatch = frontmatter.match(/series:\s*["']?([^"'\n]+)["']?/);
if (seriesMatch) metadata.series = seriesMatch[1].trim();
```

插在 `categoryMatch` 那段后面即可。**注意**：这个函数是飞书文档和本地 md 的共用入口（CLAUDE.md 里写明的规则）。如果 `lib/feishu.ts` 是直接把飞书文档的原始文本喂给 `parseBlogMetadata`，那这一改两条链路自动生效；如果飞书那边是自己独立映射字段、没走这个函数，就得在 `lib/feishu.ts` 里单独补 `series` 映射——这一点需要照着 `lib/feishu.ts` 的实际代码核实，不能想当然，否则就是"两源解析规则各自漂移"的破窗第一块。

### ③ 新建 `app/src/data/series.ts` —— 系列封面登记表

系列封面不属于任何一篇文章，不能塞进某一篇的 frontmatter（要么每篇重复写一遍造成冗余，要么隐式约定"以第一篇为准"，顺序一变封面就跟着崩）。系列封面是系列本身的属性，必须有独立的登记处：

```ts
/**
 * [INPUT]: 无外部依赖，是系列元数据的唯一定义源
 * [OUTPUT]: 对外提供 SeriesInfo 类型与 seriesRegistry 映射（系列名 -> 封面相对路径）
 * [POS]: data/ 层的系列元数据登记表，与 blogs.ts 里按文章 series 字段做的分组逻辑配对使用。
 *        系列封面独立于任何单篇文章而存在，因此不进 BlogPost 类型也不进某一篇 frontmatter
 * [PROTOCOL]: 变更时更新此头部，然后检查 CLAUDE.md
 */
export interface SeriesInfo {
  name: string;
  cover: string; // 相对路径，规则同本地文章封面：相对路径会被自动补 BASE_URL 前缀
}

// 新增系列 = 加一行 + 把封面图丢进 app/public/covers/series/
// key 必须和文章 frontmatter 里的 series: 值逐字一致，这是唯一的关联方式
export const seriesRegistry: Record<string, SeriesInfo> = {
  'AI 转型指南': {
    name: 'AI 转型指南',
    cover: 'covers/series/ai-transformation.svg',
  },
};
```

图片放 `app/public/covers/series/*.svg`（不是 `content/posts/covers/`）——本地文章封面走的是构建期 glob 内联那套机制，是给"文章"用的；系列封面数量少、手工维护，直接扔 `public/` 让 Vite 原样拷贝进产物就够了，不需要为几张图再造一套 glob（YAGNI）。

### ④ `app/src/data/blogs.ts` —— 分组是纯函数，不是新的数据源

关键决策：**分组逻辑不重新发起 fetch，而是对已有的 `BlogPost[]` 做同步变换**。原因是 `getPostsByCategory`、`getPostsByTag`、`searchPosts` 现有的模式就是"拿到列表 → 一次纯变换"，分组照抄这个模式，而不是自己再去掉一次 `getBlogPosts()`——否则列表页做分类筛选/搜索时，分组结果跟筛选结果对不上,数据源模式（feishu/static/auto）也被迫和分组逻辑耦合，两条本该独立的关注点就绞在一起了。

```ts
import { seriesRegistry } from './series';

export interface SeriesGroup {
  name: string;
  cover: string;
  posts: BlogPost[];
}

// resolveCover 原来是模块内私有函数，加 export——它就是个通用的相对路径解析器，
// 系列封面和文章封面遵守同一条 BASE_URL 规则，复用而非另写一份
export const resolveCover = (cover: string): string =>
  !cover || /^(https?:)?\/\//.test(cover) || cover.startsWith('/')
    ? cover
    : `${import.meta.env.BASE_URL}${cover}`;

/**
 * 对一批文章按 series 字段分组。系列内部按日期升序（阅读顺序），
 * 系列之间按各自最新一篇的日期降序；无 series 字段的文章归入 ungrouped
 */
export function groupPostsBySeries(posts: BlogPost[]): {
  groups: SeriesGroup[];
  ungrouped: BlogPost[];
} {
  const grouped = new Map<string, BlogPost[]>();
  const ungrouped: BlogPost[] = [];

  posts.forEach(post => {
    if (!post.series) {
      ungrouped.push(post);
      return;
    }
    const list = grouped.get(post.series) ?? [];
    list.push(post);
    grouped.set(post.series, list);
  });

  const groups = Array.from(grouped.entries())
    .map(([name, seriesPosts]) => {
      if (import.meta.env.DEV && !seriesRegistry[name]) {
        // 系列名拼错 = 静默丢封面，这个坑必须在开发期就炸出来，不能留到线上才发现
        console.warn(`系列 "${name}" 未在 seriesRegistry 登记封面`);
      }
      return {
        name,
        cover: resolveCover(seriesRegistry[name]?.cover ?? ''),
        posts: seriesPosts.sort((a, b) => a.date.localeCompare(b.date)),
      };
    })
    .sort((a, b) => b.posts.at(-1)!.date.localeCompare(a.posts.at(-1)!.date));

  return { groups, ungrouped };
}
```

`resolveCover` 原本是 `staticBlogPosts` 构建那段的局部函数，加 `export` 后原有调用点不受影响。

### ⑤ `pages/Blog.tsx` —— 列表页接分组

我这没有这个文件当前的源码，接入点按契约给，具体 JSX 结构你对着现有的卡片渲染改：

```tsx
import { groupPostsBySeries } from '@/data/blogs';

// filteredPosts 是页面现有的"筛选/搜索后的最终列表"那个变量，不要新建 state 重新 fetch
const { groups, ungrouped } = useMemo(

        <div className="flex items-center gap-4 mb-4">

          <span className="text-sm text-muted-foreground">{group.posts.length} 篇</span>

          {group.posts.map(post => <BlogCard key={post.id} post={post} />)}
        </div>
      </section>

    {ungrouped.length > 0 && (
      <section>
        {groups.length > 0 && <h2 className="text-xl font-semibold mb-4">其他文章</h2>}
        <div className="grid gap-4 md:grid-cols-3">

  </>

```

## 2. 品味自检

- **SRP**：`series.ts` 只管"系列名→封面"这一件事，`groupPostsBySeries` 只管分组变换，两者不越界。
- **DRY**：封面路径解析复用现有 `resolveCover`，没有为系列封面另写一套 BASE_URL 拼接逻辑。frontmatter 解析复用 `category` 的正则模式，没有引入新的解析范式。
- **OCP**：新增系列只需要在 `seriesRegistry` 加一行 + 文章 frontmatter 写一行，不用改分组函数或页面逻辑。
- **YAGNI**：没有为系列引入独立的排序字段、独立的路由页、独立的 glob 扫描——用户要的三点，就只做这三点该做的事。
- **唯一的隐患**：`seriesRegistry` 靠字符串精确匹配关联，系列名打错字就是静默丢封面，这不是"晦涩"而是"脆弱"——已经用 dev-only console.warn 兜底，算是在简单和安全之间选了个还算体面的平衡点，没有为此引入枚举类型或校验框架（过度设计）。

## 3. 改进建议

- 系列内排序目前用文章日期升序代替"阅读顺序"，如果日后有系列文章需要乱序发布、按人工指定顺序阅读，再加 `seriesOrder?: number` 到 frontmatter——现在不需要，先别加。
- `BlogDetail` 页面可以加一句"本文属于系列 XXX，查看其他 N 篇"的面包屑，导流效果会不错，但不在这次三点需求范围内，等你要的时候再做。
- `parseBlogMetadata` 整体是手写正则拼出来的伪 YAML 解析，这次只是照着已有模式加了一行，没有借机重构——但这堆正则迟早会在某个含逗号的中文标题上炸雷，值得记一笔账，不是这次的事。
