老杨来了。系列文章这个需求本质上是"给博客加一个新的分组维度"，落地点就三处：解析层认识这个字段、数据层把它变成结构、展示层按结构渲染。封面图不挂在文章身上，这点必须先讲清楚——否则会犯"数据泥团"的错误。

## 核心实现

### 1. `app/src/types/blog.ts` — 加两个契约

```typescript
export interface BlogPost {
  id: string;
  title: string;
  excerpt: string;
  content: string;
  coverImage: string;
  category: string;
  tags: string[];
  date: string;
  readTime: number;
  series?: string;  // 新增：所属系列名，可选——不是每篇文章都属于系列
}

export interface SeriesMeta {
  name: string;
  cover: string; // 本地相对路径，规则同 BlogPost.coverImage
}
```

`series` 必须是可选字段、不给默认值。`category`/`tags` 缺失时 markdown.ts 会兜底成 `'未分类'`/`[]`，但 `series` 不行——给它兜底成任何字符串，都会把毫不相干的单篇文章意外分进同一组。

### 2. `app/src/lib/markdown.ts` — 认识 `series:` 这一行

在 `categoryMatch` 旁边加一行，不设默认值：

```typescript
const seriesMatch = frontmatter.match(/series:\s*["']?([^"'\n]+)["']?/);
if (seriesMatch) metadata.series = seriesMatch[1].trim();
```

放在"设置默认值"那段代码**之前**，且不在默认值段落里加 `if (!metadata.series) ...`。飞书文档和本地 md 共用这一个解析器，所以飞书文档里只要写了同样的 `series:` 元数据行，两条链路自动同时支持，不用碰 `lib/feishu.ts`。

### 3. 新文件 `app/src/content/series.ts` — 系列封面清单

这是关键设计决策：**系列封面不写进任何一篇文章的 frontmatter**。系列不属于某一篇文章，挂在文章身上会导致同系列的 N 篇文章各自声明一个封面、迟早互相打架。单独建一份清单，一个系列名对应一张封面图，单一数据源。

```typescript
/**
 * [INPUT]: 依赖 @/types/blog 的 SeriesMeta 契约
 * [OUTPUT]: 对外提供 seriesManifest —— 系列名到封面图的映射清单
 * [POS]: content/ 层的系列元数据来源，被 data/blogs.ts 的 groupBySeries 消费。
 *        封面不挂在文章 frontmatter 上：系列不隶属于任何一篇文章，
 *        挂上去会导致同系列多篇文章各写各的封面、彼此漂移
 * [PROTOCOL]: 变更时更新此头部，然后检查 CLAUDE.md
 */
import type { SeriesMeta } from '@/types/blog';

export const seriesManifest: SeriesMeta[] = [
  { name: 'AI 转型指南', cover: 'covers/series/ai-transform.svg' },
];
```

封面图实体放 `app/src/content/covers/series/`，与现有文章封面 `covers/*.svg` 同一套相对路径约定。新增一个系列 = 加一张图 + 在这个数组里加一行，不碰其他文件。

### 4. `app/src/data/blogs.ts` — 分组是纯函数，不是新的数据源

不要为系列再开一条 async 抓取链路（会导致对飞书重复请求、状态不同步）。系列分组应该是对 `getBlogPosts()` 已经拿到的结果做**同步纯函数分组**，这样它对 feishu/static/auto 三种模式天然通用，且能配合现有的分类/标签筛选。

```typescript
import { seriesManifest } from '@/content/series';

// ... 在 resolveCover 定义之后加：
const resolvedSeriesManifest = seriesManifest.map(s => ({ ...s, cover: resolveCover(s.cover) }));

export interface SeriesGroup {
  name: string;
  cover: string;
  posts: BlogPost[];
}

/**
 * 按 series 字段分组，未标 series 的文章不出现在结果里
 */
export function groupBySeries(posts: BlogPost[]): SeriesGroup[] {
  const groups = new Map<string, BlogPost[]>();
  for (const post of posts) {
    if (!post.series) continue;
    const list = groups.get(post.series);
    if (list) list.push(post);
    else groups.set(post.series, [post]);
  }

  return Array.from(groups.entries()).map(([name, seriesPosts]) => {
    const meta = resolvedSeriesManifest.find(s => s.name === name);
    return {
      name,
      // 清单里没登记封面时，兜底用系列内第一篇文章的封面——不是占位假图
      cover: meta?.cover ?? seriesPosts[0].coverImage,
      posts: [...seriesPosts].sort((a, b) => b.date.localeCompare(a.date)),
    };
  });
}

/**
 * 不属于任何系列的文章
 */
export function getStandalonePosts(posts: BlogPost[]): BlogPost[] {
  return posts.filter(post => !post.series);
}
```

L3 头部要同步更新 `[OUTPUT]` 一行，把新导出的函数加进去：

```
[OUTPUT]: 对外提供 getBlogPosts/getBlogPost 读取、getCategories/getTags 聚合、
          getPostsByCategory/getPostsByTag/searchPosts 筛选、groupBySeries/getStandalonePosts
          系列分组、setDataSourceMode 与 clearCache 控制
```

`[POS]` 补一句：系列分组是对 `getBlogPosts()` 结果的纯函数二次加工，不引入新的抓取路径，三种数据源模式天然复用。

### 5. 列表页 `app/src/pages/Blog.tsx` — 按系列分区渲染

这个文件我没有原文（工具权限没给到，没法读取现有实现），但接入点很明确，改动量很小：

```tsx
import { getBlogPosts, groupBySeries, getStandalonePosts } from '@/data/blogs';

// 现有 useEffect 里拿到 posts 之后：
const seriesGroups = groupBySeries(posts);
const standalonePosts = getStandalonePosts(posts);
```

渲染部分——**只在无筛选条件（全部分类 + 无搜索词 + 无标签筛选）时走分组视图**，一旦用户筛选分类/标签/搜索，退回现有的扁平列表。这不是偷懒，是必须的：系列分组和"按分类筛选"是两种正交的视图，筛选结果里出现"半个系列+一堆孤立文章"会比不分组更让人困惑。

```tsx
{isDefaultView ? (
  <>
    {seriesGroups.map(group => (
      <section key={group.name} className="mb-12">
        <div className="flex items-center gap-4 mb-4">
          <img

            alt={group.name}
            className="w-24 h-16 object-cover rounded-lg"
          />
          <h2 className="text-xl font-semibold">{group.name}</h2>
          <span className="text-sm text-muted-foreground">{group.posts.length} 篇</span>
        </div>
        <div className="grid gap-4 sm:grid-cols-2 lg:grid-cols-3">
          {group.posts.map(post => (
            <BlogCard key={post.id} post={post} /> // 复用现有卡片渲染，无论是组件还是内联 JSX
          ))}
        </div>
      </section>
    ))}

    {standalonePosts.length > 0 && (
      <section>
        <h2 className="text-xl font-semibold mb-4">单篇文章</h2>
        <div className="grid gap-4 sm:grid-cols-2 lg:grid-cols-3">
          {standalonePosts.map(post => <BlogCard key={post.id} post={post} />)}
        </div>
      </section>
    )}
  </>
) : (
  // 现有的扁平渲染逻辑，原样保留
)}
```

若现有页面里文章卡片是内联 JSX 而非独立 `BlogCard` 组件，把原来 `posts.map(...)` 那段渲染函数体原样搬进两个 `.map()` 里即可，不需要额外抽组件。

## 品味自检

- **DRY**：飞书和本地 md 共用同一个 `parseBlogMetadata`，加字段只改一处，两条链路零延迟同步——这是这个项目原有设计就做对的事，我没有破坏它。
- **数据泥团警惕**：系列封面差点被我写成"每篇文章 frontmatter 里加 `seriesCover` 字段"，这是错的方向——N 篇文章共同拥有一个属性，就该有一个独立的家，不该分摊到每个个体上重复声明。`content/series.ts` 就是这个家。
- **YAGNI**：没有加系列详情页、没有加"上一篇/下一篇系列导航"、没有给系列加排序字段——这些都不在三条需求里，加了就是过度设计。见下面改进建议，但没写代码。
- **一个假设需要你验证**：`lib/feishu.ts` 我没有看到源码，只是根据 CLAUDE.md 里"两源共用 parseBlogMetadata"这句话推断飞书文档也会走同一个解析入口。如果飞书那边解析元数据用的是另一套逻辑（不是直接调用 `parseBlogMetadata`），`series` 字段在飞书源下会失效，需要单独确认 `lib/feishu.ts` 里调用点。
- **`Blog.tsx` 是盲改**：因为工具权限没给到，我没能读取这个文件的现有实现，上面给的是接入点和渲染骨架，不是逐行替换的 diff。落地时按现有的筛选状态变量名对齐 `isDefaultView` 的判断条件。

## 改进建议（不在本次范围内，仅供参考）

- 系列内文章目前按 `date` 倒序，如果系列本身有阅读顺序（如"第一课/第二课"），未来可以在 frontmatter 加 `seriesOrder: 1` 之类的字段做正序排列。
- `BlogDetail.tsx` 详情页可以加"本系列其他文章"侧栏，复用 `groupBySeries` 找到同系列文章即可，不需要新逻辑。
- 系列多了之后可以加一个 `/series/:name` 独立页面，但三篇系列文章体量下没必要，等真的攒够素材再做。
