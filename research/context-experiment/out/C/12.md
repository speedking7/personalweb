老杨来了。系列文章这个需求不复杂，但有一个坑要提前排掉：系列封面属于"系列"这个概念本身，不属于任何一篇文章，不能从 frontmatter 里长出来，必须单独找个地方登记——就像 giscus.ts 那样，"只有这一个填写位"。按这个思路，方案如下。

## 1. 核心实现

### 改动一：`app/src/types/blog.ts`
加 `series` 可选字段，加分组契约。这个文件目前连 L3 头都没有，顺手补上（协议要求：发现缺失立即补，阻塞级）。

```ts
/**
 * [INPUT]: 无外部依赖，纯类型定义
 * [OUTPUT]: 对外提供 BlogPost、SeriesGroup 类型契约
 * [POS]: types/ 层的博客领域模型，是 lib/markdown、data/blogs、data/series 与所有博客页面共同依赖的契约源头
 * [PROTOCOL]: 变更时更新此头部，然后检查 CLAUDE.md
 */

export interface BlogPost {
  id: string;
  title: string;
  excerpt: string;
  content: string;
  coverImage: string;
  category: string;
  tags: string[];
  date: string;
  readTime: number;
  series?: string; // 无此字段 = 不属于任何系列，不强行归类
}

export interface SeriesGroup {
  series: string;
  cover: string;
  posts: BlogPost[];
}
```

### 改动二：`app/src/lib/markdown.ts`
在 `categoryMatch` 旁边加一行 `seriesMatch`，不设默认值——没写 `series` 就是没有系列，不能像 `category` 那样兜底成"未分类"，否则每篇普通文章都会被拉进一个叫 undefined 的假分组。

```ts
const seriesMatch = frontmatter.match(/series:\s*["']?([^"'\n]+)["']?/);
if (seriesMatch) metadata.series = seriesMatch[1].trim();
```

因为飞书和本地 md 共用这一个解析函数，飞书文档里写 `series:` 元数据也会自动生效，不用碰 `lib/feishu.ts`。

### 改动三（新文件）：`app/src/lib/assets.ts`
把 `blogs.ts` 里那个内联的 `resolveCover` 提出来。原因：现在有两类资源要走同一套"本地相对路径 + 部署 base 前缀"规则——文章封面和系列封面。继续留在 `blogs.ts` 里私有，`series.ts` 就拿不到，会被迫抄一份或者反向 import 造成循环依赖。提出来是唯一干净的解法。

```ts
/**
 * [INPUT]: 依赖 import.meta.env.BASE_URL
 * [OUTPUT]: 对外提供 resolveCover —— 把本地相对路径的封面图补上部署 base 前缀
 * [POS]: lib/ 层的资源路径解析器，是文章封面与系列封面的共同入口。
 *        两类封面必须共用同一条 base 前缀规则，否则本地能看见、线上 404 的坑会在系列封面上重演一次
 * [PROTOCOL]: 变更时更新此头部，然后检查 CLAUDE.md
 */
export const resolveCover = (cover: string): string =>
  !cover || /^(https?:)?\/\//.test(cover) || cover.startsWith('/')
    ? cover
    : `${import.meta.env.BASE_URL}${cover}`;
```

### 改动四（新文件）：`app/src/data/series.ts`
系列封面的唯一登记表，纯手工维护，不从文章推导。

```ts
/**
 * [INPUT]: 依赖 @/lib/assets 的 resolveCover
 * [OUTPUT]: 对外提供 getSeriesCover —— 按系列名查询封面图(已补全部署前缀)
 * [POS]: data/ 层的系列元数据唯一填写位。系列封面不属于任何单篇文章，无法从 frontmatter 推导，
 *        只能在此手工登记；新增系列只需在这里加一行，图片本身放进 public/series-covers/
 * [PROTOCOL]: 变更时更新此头部，然后检查 CLAUDE.md
 */
import { resolveCover } from '@/lib/assets';

// 图片放 app/public/series-covers/ 下，写法与文章 frontmatter 的 cover 字段一致
const SERIES_COVER_PATHS: Record<string, string> = {
  'AI 转型指南': 'series-covers/ai-transform.svg',
};

export function getSeriesCover(series: string): string {
  const path = SERIES_COVER_PATHS[series];
  return path ? resolveCover(path) : '';
}
```

新增系列时，改这一个文件，加一行映射，把图丢进 `app/public/series-covers/`，跟文章封面的操作方式完全一致——不需要用户学第二套规则。

### 改动五：`app/src/data/blogs.ts`
删掉本地的 `resolveCover` 定义，改成从 `@/lib/assets` 导入；新增 `getSeriesGroups` / `getUnseriesedPosts`。因为它们都基于 `getBlogPosts()` 二次加工，飞书/静态/auto 三态降级逻辑是白拿的，不用重写一遍。

```ts
import { resolveCover } from '@/lib/assets';
import { getSeriesCover } from './series';
import type { BlogPost, SeriesGroup } from '@/types/blog';

// ... 原有的 staticBlogPosts 等逻辑不变，只是 resolveCover 换成 import 来的

/**
 * 按系列分组博客文章
 * 只有带 series 字段的文章才会被分组，没写 series 的文章不会被强行归类
 */
export async function getSeriesGroups(): Promise<SeriesGroup[]> {
  const posts = await getBlogPosts();
  const groups = new Map<string, BlogPost[]>();
  for (const post of posts) {
    if (!post.series) continue;
    const list = groups.get(post.series) ?? [];
    list.push(post);
    groups.set(post.series, list);
  }
  // 系列内按时间正序——系列是按顺序读的，跟外层列表"最新在前"是两回事，别用同一个排序
  return Array.from(groups.entries()).map(([series, seriesPosts]) => ({
    series,
    cover: getSeriesCover(series),
    posts: seriesPosts.sort((a, b) => a.date.localeCompare(b.date)),
  }));
}

/**
 * 不属于任何系列的文章，供列表页兜底渲染成普通条目
 */
export async function getUnseriesedPosts(): Promise<BlogPost[]> {
  const posts = await getBlogPosts();
  return posts.filter(post => !post.series);
}
```

L3 头部同步更新（INPUT 加 `@/lib/assets`、`@/data/series`；OUTPUT 加 `getSeriesGroups`/`getUnseriesedPosts`）。

## 2. 品味自检

- 没有循环依赖：一开始想让 `series.ts` 直接从 `blogs.ts` 拿 `resolveCover`，会跟 `blogs.ts` 反向 import `series.ts` 撞车，改成两边都从 `lib/assets.ts` 拿，干净。
- 没有假数据：`series` 字段没写就是 `undefined`，不兜底成"未系列"，跟这份代码里 `getCategories` 已经吃过亏、特意不写死分类的教训是同一个道理，风格统一。
- 没有过度设计：系列元数据只加了 `cover` 一个字段，没有预先加 `description`、`order` 这些没人要的东西。真需要再加，现在加是臆测。
- 唯一值得多看一眼的地方：`getSeriesGroups` 里系列内部排序（正序）跟 `staticBlogPosts` 全局排序（倒序）方向相反，是故意的，但容易被后人当成 bug"修"回去，我在注释里点了一句，别删。

## 3. 改进建议

- `SERIES_COVER_PATHS` 是硬编码映射，加新系列要改代码、走一次构建部署。量小的时候没问题，如果系列数量涨到需要运营频繁调整封面的程度，再考虑挪成飞书里的配置文档——现在没这个需求，不要提前做。
- `Blog.tsx` 我没有源码，接的时候注意确认现有的 `useState`/`useEffect` import 和分类筛选变量名，别重复引入。
- 系列封面缺失时组件直接不渲染图片（静默降级），这跟 `giscus.ts` "缺配置就显式提示"的哲学不是一回事——giscus 缺配置代表功能不可用，系列封面缺配置只是少张图，不影响阅读，两者严重度不同，所以处理方式故意不同，别为了"风格一致"硬改成显式警告。
