老杨。系列文章这个需求本质上是给 `BlogPost` 加一个可选的分组维度，外加一张与文章无关、与"系列"这个概念绑定的封面图。核心矛盾在于：封面属于系列，不属于任何一篇文章，所以不能靠 frontmatter 字段重复堆——那是数据泥团的前兆。方案如下。

## 1. 核心实现

### `app/src/types/blog.ts` —— 加一个可选字段

```ts
export interface BlogPost {
  id: string;
  title: string;
  excerpt: string;
  content: string;
  coverImage: string;
  category: string;
  tags: string[];
  date: string;
  readTime: number;
  series?: string;   // 新增：所属系列名，无系列时不存在（不是空字符串）
}
```

### `app/src/lib/markdown.ts` —— frontmatter 增加 series 提取

在 `categoryMatch` 那段旁边加一行，注意：**不给默认值**。category 缺失时兜底成"未分类"是合理的（每篇文章总要有个分类），但 series 缺失就该是 `undefined`——"不属于任何系列"本身是有意义的状态，不能伪造成某个假系列。

```ts
    const seriesMatch = frontmatter.match(/series:\s*["']?([^"'\n]+)["']?/);
    if (seriesMatch) metadata.series = seriesMatch[1].trim();
```

插入位置：紧跟 `categoryMatch` 块之后，在"设置默认值"那段**之前**（那段不需要碰，series 本就不该出现在默认值列表里）。

### `app/src/data/blogs.ts` —— 导出 `resolveCover`

系列封面和文章封面走同一套本地路径解析规则（base path 前缀、绝对 URL 直通），没道理重写一遍。只改一个字：

```ts
// 改动前: const resolveCover = ...
export const resolveCover = (cover: string): string =>
  !cover || /^(https?:)?\/\//.test(cover) || cover.startsWith('/')
    ? cover
    : `${import.meta.env.BASE_URL}${cover}`;
```

L3 头部的 OUTPUT 行同步补一项（GEB 协议要求文档与导出同构）：

```
[OUTPUT]: 对外提供 getBlogPosts/getBlogPost 读取、getCategories/getTags 聚合、
          getPostsByCategory/getPostsByTag/searchPosts 筛选、setDataSourceMode 与
          clearCache 控制、resolveCover 本地资源路径解析
```

### 新建 `app/src/data/series.ts` —— 系列聚合器

这是唯一需要新建的文件。它单向依赖 `blogs.ts`（不反向依赖，避免循环），职责单一：把已经取好的 `BlogPost[]` 按 `series` 字段分组，并配上封面。

```ts
/**
 * [INPUT]: 依赖 @/data/blogs 的 getBlogPosts 取文章、resolveCover 解析本地资源路径；
 *          @/types/blog 的 BlogPost 契约
 * [OUTPUT]: 对外提供 getSeriesGroups（系列分组+封面）、getPostsBySeries（单系列筛选）
 * [POS]: data/ 层的系列聚合器，单向依赖 blogs.ts。系列封面走手工登记表 SERIES_COVERS，
 *        键必须与文章 frontmatter 的 series 值逐字相同——未登记的系列不报错也不显示假图，
 *        而是退回该系列首篇文章自身的封面，因为兜底必须是真实资源，不是占位图
 * [PROTOCOL]: 变更时更新此头部，然后检查 CLAUDE.md
 */
import { getBlogPosts, resolveCover } from './blogs';
import type { BlogPost } from '@/types/blog';

// ============================================================
// 系列封面登记表：键 = frontmatter 里 series 字段原文
//               值 = 相对 public/ 的路径
// 新增系列 = 加一行 + 把图丢进 app/public/series-covers/
// ============================================================
const SERIES_COVERS: Record<string, string> = {
  'AI 转型指南': 'series-covers/ai-transformation.svg',
};

export interface SeriesGroup {
  name: string;
  cover: string;
  posts: BlogPost[];
}

/**
 * 按系列分组文章，未标注 series 的文章不出现在结果里。
 * 系列间按各自最新一篇的日期降序排列，与全站"最新在前"的既有约定一致。
 */
export async function getSeriesGroups(): Promise<SeriesGroup[]> {
  const posts = await getBlogPosts();
  const groups = new Map<string, BlogPost[]>();

  for (const post of posts) {
    if (!post.series) continue;
    const list = groups.get(post.series) ?? [];
    list.push(post);
    groups.set(post.series, list);
  }

  return Array.from(groups.entries())
    .map(([name, seriesPosts]) => {
      const sorted = seriesPosts.sort((a, b) => b.date.localeCompare(a.date));
      const registered = SERIES_COVERS[name];
      return {
        name,
        cover: registered ? resolveCover(registered) : sorted[0].coverImage,
        posts: sorted,
      };
    })
    .sort((a, b) => b.posts[0].date.localeCompare(a.posts[0].date));
}

/** 按系列名筛选文章，供系列详情/筛选视图使用 */
export async function getPostsBySeries(name: string): Promise<BlogPost[]> {
  const posts = await getBlogPosts();
  return posts
    .filter(post => post.series === name)
    .sort((a, b) => b.date.localeCompare(a.date));
}
```

物理图片放 `app/public/series-covers/*.svg`（或 png/webp），跟现有 `public/covers/` 是同一个约定——public/ 下的东西 build 时原样拷进 `docs/`，不需要动 `vite.config.ts`。

## 2. 品味自检

- **SRP**：`series.ts` 只做一件事——分组+配封面，不碰数据源判断（feishu/static/auto），那是 `blogs.ts` 的地盘，没有越界。
- **DRY**：封面路径解析复用 `resolveCover`，没有为系列封面另起一套逻辑。
- **KISS**：分组逻辑建立在已经拿到手的 `BlogPost[]` 之上，不关心这些文章来自飞书还是本地——比 `getCategories`/`getTags` 那种要单独调 `feishuBlogClient.getCategories()` 的实现反而更干净，因为 `series` 从一开始就是纯前端的展示分组，不需要飞书侧的特殊感知。
- **YAGNI**：没有加系列排序字段（第几部分）、没有加系列描述字段——需求没提，不造。
- **数据泥团警惕**：没有让每篇文章的 frontmatter 都写一遍封面路径，那样任何一次改封面都要改 N 个文件，而且极易出现同系列文章封面不一致的脏数据。

## 3. 改进建议

- **登记表的脆弱点**：`SERIES_COVERS` 用系列显示名字符串做键，跟每篇文章 frontmatter 里的 `series` 值必须逐字相同。改名、打错字都会导致封面静默丢失（不报错，退到兜底）。现在按你给的格式（`series: 显示名`）先这么做没问题，但如果系列数量涨起来，建议后续把 `series` 字段换成稳定的 slug（如 `series: ai-transformation`），显示名和封面都从登记表统一派生，登记表变成唯一真源——避免"改一个系列名要同步改 N 篇文章"的僵化。现在不做，是因为你还没这个规模，做了就是过度设计。
- **`pages/Blog.tsx` 和 `lib/feishu.ts` 我没有源码**：接入代码给的是形状而非逐行 diff，你落地时对一下现有 category 筛选的具体写法。另外要确认 `feishu.ts` 里飞书文档转 `BlogPost` 那一步，是不是也过了 `parseBlogMetadata`——dataflow 里写的是"两源共用"，如果飞书那边是手工字段映射、没走这个函数，`series` 字段在飞书源上就会失效，需要单独补。
- **GEB 文档回环**：`data/series.ts` 是新文件，L3 头部我已经按协议写了。如果 `app/src/data/` 下存在 L2 的 `CLAUDE.md`（清单未在本次上下文提供，我看不到），需要手工把 `series.ts` 加入成员清单——这是 FATAL-004 级别的强制项，别漏。L1 根 `CLAUDE.md` 的 `data 数据入口与降级决策` 这行描述粒度够粗，不需要因为加一个文件就改。
