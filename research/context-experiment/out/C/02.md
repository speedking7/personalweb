老杨，方案如下——你要的是给"系列"这个概念找到正确的家，而不是在每篇文章里散弹式塞字段。我按现有代码的既定范式（`parseBlogMetadata` 两源共用、封面走 `BASE_URL` 相对路径解析）来接，不另起炉灶。

## 1. 核心实现

**关键决策**：系列封面不进 frontmatter。封面属于"系列"这个实体，不属于某一篇文章——写进每篇文章的 frontmatter，同系列 N 篇就要抄 N 遍同一路径，改封面要改 N 处，抄错一处就是"同系列文章封面各不相同"的诡异 bug。单独建一张登记表，是让"系列封面只有一份真相"成立的唯一做法。

### 1.1 `app/src/lib/assets.ts`（新建）

原先 `resolveCover` 逻辑写死在 `blogs.ts` 里只服务文章封面。系列封面要复用同一套"什么路径原样返回、什么路径要拼 BASE_URL"的判断，于是抽成公共函数——两处调用方必须共用一条规则，否则某天判断标准分家，就会出现"文章封面能显示、系列封面 404"这种问题。

```ts
/**
 * [INPUT]: 无（仅依赖 vite 编译期注入的 import.meta.env.BASE_URL）
 * [OUTPUT]: 对外提供 resolveAssetPath —— 本地相对路径 → 部署期真实 URL
 * [POS]: lib/ 层的资源路径解析器，是 public/ 静态资源与 frontmatter 相对路径之间的唯一桥梁。
 *        原本内嵌在 data/blogs.ts 里只服务文章封面，系列封面上线后两处必须共用同一条判断规则
 * [PROTOCOL]: 变更时更新此头部，然后检查 CLAUDE.md
 */
export const resolveAssetPath = (path: string): string =>
  !path || /^(https?:)?\/\//.test(path) || path.startsWith('/')
    ? path
    : `${import.meta.env.BASE_URL}${path}`;
```

### 1.5 `app/src/data/blogs.ts`（修改）

删掉本地的 `resolveCover`，改用共享的 `resolveAssetPath`；新增 `getSeriesGroups`。

```ts
import { feishuBlogClient } from '@/lib/feishu';
import { parseBlogMetadata } from '@/lib/markdown';
import { resolveAssetPath } from '@/lib/assets';
import { SERIES_COVERS } from './seriesCovers';
import type { BlogPost, SeriesGroup } from '@/types/blog';

export type { BlogPost, SeriesGroup };

// ... localPostModules / staticBlogPosts 不变，
// 唯一改动：resolveCover(post.coverImage) → resolveAssetPath(post.coverImage)

/**
 * 按系列分组博客文章
 * 只统计带 series 字段的文章；系列内部按发布时间正序（阅读顺序），
 * 与列表页"最新在前"的排序方向刻意相反——系列是给人按顺序读的
 */
export async function getSeriesGroups(): Promise<SeriesGroup[]> {
  const posts = await getBlogPosts();
  const groups = new Map<string, BlogPost[]>();

  posts.forEach(post => {
    if (!post.series) return;
    const existing = groups.get(post.series);
    existing ? existing.push(post) : groups.set(post.series, [post]);
  });

  return Array.from(groups.entries()).map(([name, seriesPosts]) => ({
    name,
    cover: resolveAssetPath(SERIES_COVERS[name] ?? ''),
    posts: seriesPosts.sort((a, b) => a.date.localeCompare(b.date)),
  }));
}
```

L3 头部 `[OUTPUT]` 行加上 `getSeriesGroups` 分组读取。

```tsx
import { getSeriesGroups } from '@/data/blogs';
import { SeriesCard } from '@/components/SeriesCard';
import type { SeriesGroup } from '@/types/blog';

// 与现有 posts 的 state/useEffect 并列
const [seriesGroups, setSeriesGroups] = useState<SeriesGroup[]>([]);
useEffect(() => {
  getSeriesGroups().then(setSeriesGroups);
}, []);

// 渲染：置于原有文章列表上方，不改动列表本身——非系列文章仍在下方平铺展示

  <section className="mb-12">
    <h2 className="text-2xl font-bold mb-4">系列文章</h2>
    <div className="grid grid-cols-1 sm:grid-cols-2 lg:grid-cols-3 gap-6">

        <SeriesCard key={group.name} group={group} />
      ))}
    </div>
  </section>
)}
```

设计决定：系列区块是**叠加**在原列表之上，属于系列的文章仍然出现在下方平铺列表里（不做去重隐藏）。理由：用户从"最新文章"进来，和从"系列导览"进来，是两条并行的浏览路径，互相隐藏对方会让人以为文章少了。

## 2. 品味自检

- **DRY**：`resolveAssetPath` 只写一遍，文章封面和系列封面共用，没有第二份"路径判断逻辑"存在的空间。
- **SRP**：`seriesCovers.ts` 只干一件事——系列名到封面的映射；`getSeriesGroups` 只干分组这一件事，不掺解析、不掺渲染。
- **数据泥团警惕**：没有把 `series` + `seriesCover` 两个字段捆在每篇文章上重复搬运，避免了同一份数据被抄写 N 份后各自漂移的坏味道。
- **YAGNI 边界**：没有做系列专属路由页（`/series/:name`）、没有做"上一篇/下一篇"跨系列导航——需求只要"列表页分组展示"，这些是合理但未被要求的扩展，先不做。
- **唯一妥协**：`SERIES_COVERS[name] ?? ''` 找不到封面时静默返回空字符串，`SeriesCard` 里跳过 `<img>` 渲染。这和 giscus 配置"缺配置时显式提示"的项目惯例不完全一致——如果你要更严格，可以在开发环境下对未登记的 series 打一条 `console.warn`，我没有默认加，因为系列封面缺失不影响文章可读，属于视觉降级而非功能失效。
