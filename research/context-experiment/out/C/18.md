### app/src/lib/markdown.ts —— frontmatter 里多解析一个字段

在 `categoryMatch` 那段旁边加一行,跟其它字段同一套写法,飞书文档和本地 md 共用这一个解析器,规则不会分叉:

```ts
const seriesMatch = frontmatter.match(/series:\s*["']?([^"'\n]+)["']?/);
if (seriesMatch) metadata.series = seriesMatch[1].trim();
```

不设默认值——没写 `series` 就是 `undefined`,这正是"不属于任何系列"的信号,不需要额外的哨兵值。

### app/src/data/series.ts（新文件）—— 系列封面登记表

```ts
/**
 * [INPUT]: 无外部数据依赖，纯静态登记表
 * [OUTPUT]: 对外提供 getSeriesCover —— 按系列名查封面相对路径
 * [POS]: data/ 层的系列元数据登记表。文章 frontmatter 只声明 series: 系列名，
 *        封面图不随每篇文章重复填写——新系列在此登记一次，避免同一系列的
 *        N 篇文章各自维护、迟早漂移的 N 份封面路径
 * [PROTOCOL]: 变更时更新此头部，然后检查 CLAUDE.md
 */

// 值为相对 public/ 的路径，规则与文章 cover 字段一致，
// 由 data/blogs.ts 导出的 resolveCover 统一补 base，实际图片放在 app/public/covers/series/ 下
const seriesCovers: Record<string, string> = {
  'AI 转型指南': 'covers/series/ai-transformation.svg',
};

export function getSeriesCover(name: string): string {
  return seriesCovers[name] ?? '';
}
```

图片实际存放路径:`app/public/covers/series/ai-transformation.svg`(与现有文章封面同一套 `public/covers/` 惯例,借道 Vite 的静态资源直出,不走 import 打包)。

### app/src/data/blogs.ts —— 导出 resolveCover + 新增分组函数

两处改动:

**a) `resolveCover` 加 `export`**(原本是模块内私有函数,现在系列封面也要用它补 base):

```ts
export const resolveCover = (cover: string): string =>
  !cover || /^(https?:)?\/\//.test(cover) || cover.startsWith('/')
    ? cover
    : `${import.meta.env.BASE_URL}${cover}`;
```

**b) 新增分组函数**,放在文件底部、`clearCache` 附近:

```ts
import { getSeriesCover } from './series';

export interface SeriesGroup {
  name: string;
  cover: string;
  posts: BlogPost[];
}

/**
 * 按系列对已获取的文章列表分组。
 * 有意做成同步纯函数、不重复发起请求——调用方（Blog.tsx）已经持有
 * 经过分类/标签/搜索筛选后的 posts 数组，这里只负责在其上再分一层维度
 *
 * 系列内部按创作顺序（旧→新）排列，与站内默认的新→旧相反——
 * 系列指南是有先后阅读顺序的教程，不是取最新回顾的信息流
 */
export function groupPostsBySeries(posts: BlogPost[]): { series: SeriesGroup[]; standalone: BlogPost[] } {
  const seriesMap = new Map<string, BlogPost[]>();
  const standalone: BlogPost[] = [];

  for (const post of posts) {
    if (!post.series) {
      standalone.push(post);
      continue;
    }
    const list = seriesMap.get(post.series) ?? [];
    list.push(post);
    seriesMap.set(post.series, list);
  }

  const series: SeriesGroup[] = Array.from(seriesMap.entries())
    .map(([name, seriesPosts]) => ({
      name,
      cover: resolveCover(getSeriesCover(name)),
      posts: [...seriesPosts].sort((a, b) => a.date.localeCompare(b.date)),
    }))
    .sort((a, b) => {
      const latestA = a.posts[a.posts.length - 1]?.date ?? '';
      const latestB = b.posts[b.posts.length - 1]?.date ?? '';
      return latestB.localeCompare(latestA); // 系列区块本身按最新更新时间排
    });

  return { series, standalone };
}
```

### app/src/pages/Blog.tsx —— 列表页接入分组

这个文件我手上没有源码,你贴给我的上下文里没有它。以下是套用模式,落到你现有的"筛选后拿到 posts 数组、渲染卡片网格"那一段即可,变量名按实际情况对齐:

```tsx
import { groupPostsBySeries } from '@/data/blogs';

// filteredPosts 是你现有分类/标签/搜索筛选后的结果
const { series, standalone } = groupPostsBySeries(filteredPosts);

return (
  <>

      <section key={group.name} className="mb-12">

          {group.posts.map(post => (

        </div>

    ))}

    {standalone.length > 0 && (
      <section>

          ))}
        </div>

    )}
  </>

```

## 2. 品味自检

- **SRP 到位**:`series.ts` 只管"名字→封面"这一张表,`groupPostsBySeries` 只管分组排序,`markdown.ts` 只管解析——互不越界。
- **DRY**:封面路径的 base 拼接复用了已有的 `resolveCover`,没有另起一份逻辑。
- **OCP**:加系列不改分组函数,只在登记表加一行。
- **避开了数据泥团**:系列名+封面没有散落到每篇文章的 frontmatter 里各抄一份,收敛到一张表,不会出现"这篇系列改了封面、那篇忘了改"的漂移。
- **隐患**:`series.ts` 里的名字和文章 frontmatter 里的 `series:` 是两处手写字符串,拼错一个空格就静默变成无封面孤儿(不报错,只是 cover 是空字符串)。这是唯一让我不完全满意的地方,见下条改进建议。

## 3. 改进建议

- 加一个开发期校验:`groupPostsBySeries` 里,对 `seriesMap` 中不在 `getSeriesCover` 登记表里的系列名 `console.warn`,避免拼写错误在生产环境上悄悄变成"系列存在但无封面"。
- BlogDetail 详情页可选加"本系列其他文章"侧栏,复用 `groupPostsBySeries` 按 `post.series` 过滤即可——但这超出本次需求范围,先不做,YAGNI。
- 如果系列内文章不是严格按发布日期先后写成(比如补发早年写好但延迟发布的稿子),纯日期排序会错位,届时再加 `seriesOrder?: number` frontmatter 字段做人工覆盖排序,现在没这个需求就不预先加。

GEB 头部:`types/blog.ts`、`lib/markdown.ts`、`data/blogs.ts` 的 L3 头部按上面注释更新即可;`series.ts` 是新文件,头部已经写好。若 `app/src/data/` 下已存在独立的 L2 `CLAUDE.md`,记得在成员清单里补一行 `series.ts: 系列名→封面登记表`;L1 根 CLAUDE.md 对 `data/` 的描述("数据入口与降级决策")本身够宽,不必改。
