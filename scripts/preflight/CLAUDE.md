# scripts/preflight/

> L2 | 父级: ../../CLAUDE.md

发稿前把 `BLOG_PLAYBOOK.md` 与 `OPERATIONS.md` 里那些"记着但没人跑"的规则变成可执行的检查。
在此之前，playbook 第四节写着"跑脚本，不靠感觉"，而仓库里没有那个脚本——五篇文章全靠临时拼的代码对表。

Python 而非 Node（与隔壁 `wechat/` 不统一是刻意的）：这一支的重头是像素判据，Pillow 现成，
Node 得再装 sharp；两个模块之间没有任何调用关系，为对称而统一只是徒增依赖。

## 闸门与指标的分野

这是全模块唯一重要的设计决策，其余都是它的推论。

**闸门**只拦一种东西：**页面照常渲染、功能已经死了、而且你看不出来**。
tags 写成全角逗号，标签页永远筛不出这篇；frontmatter 多写一个字段，被 `parseBlogMetadata`
静默丢弃；封面橙色点落在 85%，列表页裁掉它而文章页看着好好的。这类错的共同点是没有症状，
不主动测就永远发现不了，而封面这一类**发出去之后无法补救**。

**指标**只报数：段落均长、句均、极短段占比、「你」密度、问句密度。它们是风格问题，
看得见、随时能改、且合理值随文章类型浮动。

分野的理由是行为上的，不是分类学上的：**这个仓库没有 CI 也没有 git hook，脚本要人主动跑。**
只要有一项天天飘红，人就会开始忽略输出——然后连闸门一起忽略。所以闸门必须干净到
"红了就一定得改"。

「结尾段」这一项是被这条标准踢出闸门的：它看得见、能改，不是静默失败；
而且带附录的文章会被误判——第二篇正文结尾是 22 字冷短句，后面跟着 442 行的协议代码块，
脚本看到的"最后一段"其实是附录引导语。放指标区报数并注明这一点。

**2026-08 更要紧的是这一项的判据本身错了**：原来查的是"末段是否短于段落均长"，
而那条规则实测不成立——付费全集里末段真更短的只有 15/35，末段均长反而高于段落均长。
真正的不变量是**末段恒为一句**（免费与付费四组语料的句数中位数都是 1），
脚本已改为查末段句数。这是个提醒：**判据错了的检查比没有检查更糟**，
它会稳定地把你往错方向推，而且因为"有脚本在跑"而无人复查。

## 成员清单

`prose.py`: 文章验收。闸门六条（frontmatter 白名单、tags 半角逗号、cover 相对路径、
cover 文件存在、站内链接非死链、加粗没被标点吃掉），指标六项。
另有一条**条件闸门**：文章里出现 markdown 表格时，才查 `BlogDetail.tsx` 挂没挂 `remark-gfm`。
2026-09-06 加的，起因是第三轨首篇发出去表格全渲染成竖线文本——`react-markdown` 不带 GFM，
不挂插件时表格降级成普通段落，页面照常显示、构建不报错。
**做成条件触发而非常驻，是因为散文轨一张表都没有**，常驻的话它对那批文章永远绿着，
等于一条没有信息量的闸门；而按本文件开头那条，闸门必须每一条都值得看。

剥围栏代码块是必须的而非讲究：不剥的话讲技术的那几篇会把指标整片带偏——第二篇未剥时句均
量到 43.8 字、问句密度 1.3，全是代码块贡献的；剥掉后回到 24.8 与 3.0。同一个道理，
死链扫描也走剥过的正文，否则代码块里演示 markdown 写法的 `[文字](地址)` 会被当成真链接。
这与 `wechat/links.mjs` 用 lexer 而非正则是同一类判断。

指标**横向对比已发篇目**而不只对表手册目标值。理由是 playbook 第四节记过一次教训：
句均与极短段连续两篇几乎同一个数，那不是偶然失手而是固有偏移——只有跟历史比才分得出来。
跳出历史区间的项会被单独标出。

**2026-08 加了两层分辨率。**

其一，**按轨别分组**（`history()` 读 frontmatter 的 `category`）：入门篇只跟入门篇比。
不分组的话，第一篇实作篇带着代码块与数据表进来就会把区间整片拉宽，从此每篇都"在区间内"，
横向比失效。`TARGETS` 也按轨分——段落与句子两项两轨相同（那是作者的指纹，
同年对照实测 25.8 对 25.8），问句与人称随篇幅涨，入门轨对 8 与 20.5、实作轨对 10 与 22。

其二，**口径改为不数标点**（`words()`，只留字母/数字/汉字）。此前脚本数标点而目标值不数，
两把尺子对同一张表：长度类虚高 13%、极短段虚低 24%、人称虚低 12%。后果是照着自检
会以为"还不够碎"而继续加短段——第 4、5 篇的极短段 47.5% 与 35.1% 就是这个反馈环的产物。
`CHARS_PER_MIN` 也跟着从 459 改成 347：**口径一改，所有由口径反推的常数都得重算**，
否则它会静默漂移，而这类常数没人会去复查。

**极短段占比已降级为只报数、不设目标**（`REPORT_ONLY`）。它是高方差量：
同一批语料换取样窗口量四次得到 8%/21%/38%/6%，差值大于它想测的效应。
设目标只会诱导硬凑，而 playbook 第四节记过硬凑的下场。

`cover.py`: 封面验收。闸门四条（尺寸 1920x1072、背景通铺一色、橙色点在 1.36:1 与 1.2:1
两种裁切下存活），指标两项（全部物件存活率、文件大小）。

只把**橙色点**存活列为闸门、物件整体存活只报数，是因为 playbook 定的语义就在橙色点上——
它落在有语义的那个物件上，读者读到对应段落会回头认出封面。构图两侧被裁掉一部分是这套
左右对置视觉的常态，前四篇都如此。

存活率按"列"计，阈值取 `ALIVE = 99.5` 而非 100：边界列必然吃掉零点几个百分点，
取 100 会让永远达不到的条件长期飘红，正是上面那条要避免的事。

背景色带检测取顶部 3% 逐列采样。顶部若有物件则**明说取样不可靠并判为不通过**，
不给一个看起来精确的假数字——满幅出血的第四篇在这里会量出 124 的色差，那是物件不是色带。

`fit.py`: 唯一"加工"而非"验收"的一支，加工完自动回头跑一遍 `cover.py` 的判据。
不带参数只裁到 1920x1072（playbook 第五节那段 PIL 代码的固化）；`--inset` 再等比缩小居中，
把物件压进安全区。

安全区 `SAFE_LO/HI = 0.165/0.835` 由最严的 1.2:1 中心裁切倒推，不是拍脑袋的数。

`--inset` 与 playbook 里原有的"抽中间留白合拢"是互补而非替代：那招要求中间有富余留白，
**满幅出血时失效**；等比缩放没有这个前提，代价只是物件变小、留白变多，而这套视觉本来就是大留白。
第五篇封面就是这么救的，第四篇实测能把橙色点从 21% 存活救到 100%。

内缩的横向定位按"物件左缘对齐安全区左界"，**不是**按画布居中。原图里物件本身多半不对称
（第二篇是 8.6%~93.9%，中心在 51.25%），缩完再居中会把那份偏移原样带过去，一侧仍越界——
实测第二篇会落在 17.5%~84.5%，右边照样出安全区。改成左缘对齐后五张全部精确落在 16.5%~83.5%。

`clean_strip` 找的是"整行都是背景"的横带，不能想当然取顶部——满幅出血的图顶部也有物件，
取到就会把物件拉伸成底纹。

**带的厚度决定拉伸倍数，倍数决定纸纹会不会被抻坏。** 取 `H//40`（26 行、41 倍）实测五张
全部把横向色差放大到超容差；取 `H//10`（107 行、10 倍）才留得住。

铺完还要**自己量一次**：超容差就退回纯色。加工工具不许引入新缺陷——这条不是洁癖，
第一版正是因为没有它，把第一、二篇本来只有 2 的背景色差加工成了 6 和 7。
退回纯色时明说纸纹会丢，那是真实代价，不该藏。

`requirements.txt`: 只有 Pillow，且只有 `cover.py` 与 `fit.py` 需要。
`prose.py` 纯标准库，克隆下来即可跑。
